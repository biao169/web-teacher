# 两端网站同步：全新设计契约

日期：2026-10-05。本文保留第一步设计契约；数据库与执行器已推进到第三步，当前实现及限制见 step3.md，尚未部署。
依据：用户 MD 中的功能要求，以及本轮关于资源、流式处理、重试、网站访问和数据库的要求。
设计不引用旧版网站代码，不继承旧版类、函数、状态 JSON 或恢复链条。

## 1. 最小架构

网站后台负责鉴权、创建/确认任务、设置参数和查看状态。独立同步执行器每次推进一个步骤。
Worker 使用专用同步 Worker；Ubuntu/Debian 使用独立后台进程。后台页面仍共用教师网站。
同站共享数据库和媒体，因此仍需单并发、短事务、有限查询和访问预算。
不引入 Redis 或复杂队列框架作为默认依赖，不加载网站模板/翻译/学术查询资源。

新代码按以下职责组织；本步仅实现 core 和 prototypes，其余随步骤实现，不创建空壳功能：

| 路径（相对本交付根目录） | 职责 |
| --- | --- |
| site_sync/core/contracts.py | 小型任务类型和适配接口 |
| site_sync/core/policy.py | 重试、降速的纯逻辑 |
| site_sync/core/engine.py（后续） | 一个任务、一个阶段、一次有界推进 |
| site_sync/adapters/（后续） | SQLite/D1、文件/R2、签名对端通信 |
| site_sync/entrypoints/（后续） | Worker Cron 与本地后台进程 |
| site_sync/frontend/（后续） | 共用后台页面和交互 |
| site_sync/deploy/（后续） | 专用执行器打包与部署 |
| site_sync/tests/（后续） | 正式集成与故障恢复测试 |

网页 HTTP 请求不执行一整轮同步，不在等待网络时占用数据库写锁。
不靠浏览器保持任务运行；刷新状态只读，不能暗中推进任务。

## 2. 一个主任务、三种入口

阶段：discover → await_confirmation → transfer → apply → cleanup → done。
状态独立保存：ready、running、waiting、paused、cancel_requested、cancelled、done。
无进展慢重试只是 waiting 的原因，不创建另一套后台恢复状态机。

手动拉取：读取摘要、选择后确认一次；后台接着执行已确认范围。
定时拉取：使用预先保存的模块、增删权限和周期授权，无需每次再次确认。
推送：提交提案，接收方批准一次，再由接收方执行同一个拉取引擎。
推送双方各自保存任务，使用固定 proposal_id 关联；接收方不会因有共享密钥而允许任意写入。

任务不再分裂为准备/执行的多个本地父子任务。创建、批准和提案使用稳定操作 ID，
丢回执后查找同一次操作，不盲目重建。权限变化、对端配置变化、修改范围都必须重新核对。
退出登录不取消已确认任务。暂停会阻止下一次提交；取消先保存意图，待有效租约结束后清理。
已提交数据不回滚，归属不明的媒体不删除。

## 3. 候选与业务边界

只处理所选业务模块及必要依赖，不镜像账号、权限、系统配置。
跨所选模块合并两端最新 500 个候选；使用索引、稳定排序和游标，不先加载整库。
必要依赖另设限额。没进前 500、未入选或分页未见到不代表应该删除。
删除必须有明确删除依据及授权；本地独有媒体不自动删除。
同内容可直接覆盖，不增加全文相同比对。来源和目标版本在处理期间固定，冲突暂停相关条目。
同一记录完整提交后才对网站可见；允许多条记录之间逐步完成。
跨站身份使用稳定 UID/映射，不按两站各自的自增编号猜测对应关系。
默认只接收站启用定时拉取，避免双向自动覆盖循环。

## 4. 数据库和唯一初始化文件

只维护网站 `database/schema.sql`，同步不另设 init.sql/schema.sql。
部署脚本引用同一文件；版本迁移通过代码实现，不能靠重新执行建库脚本替代迁移。

建议最小结构：连接配置、任务主表、任务条目表、文件进度表、暂存片段表。
任务主表的高频状态使用普通列，不放大块 JSON：
task_id、phase、status、progress_seq、revision、lease_token、lease_until、grant_revision、
attempt_id、attempt_start_seq、reconciled_attempt_id、next_run_at、no_progress_count、total_errors。
任务内容与列表不随进度反复读写；索引覆盖到期任务选择及单任务条目游标。
最终表名与约束由第二步定义；内存原型表不能成为正式初始化入口。

部署自动执行：识别结构/版本 → 备份或恢复点 → 迁移互斥 → 暂停同步写入 →
分版本转换 → 核对结构和必要数据 → 切换兼容代码 → 恢复调度。
重复部署与迁移中断可恢复；未知结构停止升级，不能自动清库。
需要更替表时分批复制、检查和短切换；普通网页请求不得执行迁移。
历史任务的格式转换以后只根据明确结构实现，不能继承/猜测旧授权；无法可靠转换则保留并暂停。
SQLite 与 D1 单独验证原子能力；业务写入与进度同批次/事务完成。
数据库与对象存储不存在共同事务，媒体使用意图、固定操作 ID 与回执核对。

## 5. 真进度和重试

progress_seq 只在以下持久化事件增加：实际候选游标前进、保存正文片段、确认一个存储分段、
提交一条业务记录、真实阶段转换或清理完成。时间、日志、心跳、重试次数、降速配置、
HTTP 成功、重复确认同一回执及重建同一上传尝试均不算进度。
同任务 seq 只能前进，不能通过反复切换阶段制造进度。

| 观察结果 | 行为 |
| --- | --- |
| 报错但 seq 前进 | 保留异常统计，无进展计数清零，继续 |
| 成功且 seq 前进 | 无进展计数清零，继续 |
| 成功但 seq 不变 | 正常等待，不清零也不计失败 |
| 可恢复错误且 seq 不变 | 计一次无进展，退避并缩小适用工作量 |
| 强制终止，无结束回执 | 租约/恢复窗口后核对，不能假定回滚或仍在运行 |
| 权限/签名/明确冲突 | 保留进度并暂停，不能被重试绕过 |

一次尝试一个 attempt_id；核对后保存 reconciled_attempt_id，避免重复计错。
同一提交同时校验租约令牌、授权版本、记录/来源版本及期望进度。
后台显示“连续无进展快速重试次数”，默认 Worker 30、本地 8；N=0 表示首次失败就转慢重试。
初次失败后有 N 次快速恢复机会；额度用完后的无进展错误转慢重试，不关闭后台授权。
Worker 快速退避 60/180/600 秒，本地拟采用 5/15/60 秒；慢重试默认每小时/每 15 分钟。
本步 policy.py 实现的是 Worker 退避参数，本地参数接入随执行器实现。
任务无总时长上限；有进度就继续。成功后不立刻提速，避免反复触碰资源上限。
1102 按资源异常处理；1101 记录具体原因，不能笼统认定为切片过大。
最小粒度仍无法执行时，进入低频等待并显示原因，不宣布任务必然可以完成。

## 6. 切片和文件流

正文以字节 offset/length 记录，允许在同一内容传输中缩小下一片；来源版本不能变。
UTF-8/JSON 跨片使用正确解码边界，不能把字节位置当字符位置。
Worker 正文切片暂定 1 KiB、最低 256 B，最终默认值须实测；应用层有硬上限。
准备、字段转换、引用提取和最后写入都需有界；不能下载分片、提交时又加载整个任务。
先保留单条 200000 字节约束，第二步验证长字段在库内组装及完整记录原子提交。

媒体分清三个概念：传输范围、运行时流缓冲、R2 存储 part。
R2 part 固定从 5 MiB 起，最后一段可短；4 KiB 缓冲不能作为 multipart part。
响应原生流直接进入存储，减少 Python/JS 转换、Base64 与多次全文哈希。
part 内尚未持久化的字节不是进度，失败只能重试该 part；本地文件可更细粒度续传。
同一 R2 上传不能任意改变 part 宽度；后台正文切片参数和媒体参数必须分别展示。
小文件可直接流式 PUT，但 PUT 失败需要重新传该文件。

来源使用稳定版本和准确 Range；不允许压缩改变范围。写入唯一暂存对象，完成后核对
总长度、来源和操作归属，再提交业务引用。完成回执丢失则先 HEAD，不再次盲目合并。
R2 multipart ETag 不作为通用 SHA-256。默认七天未完成上传清理与慢任务生命周期需协调；
上传失效仅重建当前文件上传，其他已完成记录保留，重复重建不虚增进度。

原型 forwardPart 演示原流转交，completeFile 演示长度/归属/来源核对。
原型不包含签名 HTTP 服务、真实 R2 SDK、D1 或 Python FFI，因此不能直接作为生产接口。

## 7. 后台、调度与日志

后台参数：快速重试次数、正文切片/下限、存储能力允许的媒体参数、自动降速、慢重试间隔。
状态显示完整任务 ID、阶段、持久化记录/字节、最近有效进展、无进展次数、累计异常、
下次允许时间及调度到达。UTC 存储，统一后台 IANA 时区，默认 Asia/Shanghai。
Worker 暂定单条五分钟 Cron，每轮一个有界步骤；冷却任务让行，无请求内休眠。
等待到期只代表允许执行，实际执行依赖下一次调度。
网页与同步执行资源隔离仍不消除 D1/R2/账户配额竞争，需并发访问测试。
免费 Cron 不会因延长周期获得更多 CPU 额度；不能用墙钟耗时替代平台 CPU 指标。
日志按阶段/异常聚合，不逐片写完整日志；清理历史和孤立暂存，但保护活动慢任务。
网站缓存只在真实业务提交后失效，不缓存整个同步任务正文。

## 8. 分步落地

1. 本步：需求契约、核心接口/策略、独立提交和流式原型、本地验证。
2. 数据结构：唯一 SQL、SQLite/D1 正式存储适配、部署自动检验与迁移。
3. 执行引擎：单任务阶段、授权/租约、进度、幂等提交及恢复。
4. 传输：正文切片、原生媒体流、文件发布与丢回执核对。
5. 部署：专用同步 Worker/本地进程、共用后台、单一调度入口。
6. 管理：参数、任务监控、错误聚合和暂存清理。
7. 实机验收：双向部署组合、故障注入、长任务与正常网页并发访问。
