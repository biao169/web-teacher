# 第三步：统一任务执行器

本步从第二步新模块继续开发，不使用旧版网站代码。没有连接或部署任何真实网站。

## 已实现

- core/engine.py：每次 tick 先核对一个逾期回执，或只调用一个阶段处理器；没有等待循环。
- core/authority.py：当前授权、范围、有效期、对端修订、数据库版本和租约的提交守卫。
- adapters/tasks.py：创建、确认、领取、阶段推进、写入、暂停、继续、取消、清理和恢复。
- adapters/staging.py：正文提交同时校验可写授权、被选中条目和最新授权修订。
- database/schema.sql：结构版本 2，新增授权表及任务确认/取消字段，仍只有一个初始化 SQL。
- deploy/migrations.py：第二步 schema 1 → 本步 schema 2 的明确自动升级。
- examples/demo.py：可运行的内存数据库完整流程示例。
- tests/test_engine.py：执行器、授权、并发及实际版本升级验证。

## 三种任务

手动拉取：discover 后停在 await_confirmation；confirm 绑定选定条目和授权修订，
同一确认请求重放不重复操作。预览授权不能写业务。
定时拉取：create(mode='scheduled') 必须具备写权限；discover 完成后可进入 transfer，
未授权的删除候选不会自动选中。
推送提案：接收站使用 mode='proposal' 创建任务，仍必须明确 confirm；
本步未实现发送提案的网络接口，第四步接入传输层。

阶段处理器由服务器代码注入，不接受浏览器提交的 SQL、函数或权限声明。
Handler 每轮必须执行有界工作；框架只调用一个 handler，但不会把任意无界 handler 自动变成低 CPU。
完整流程示例使用内存业务表，展示 discover → transfer → apply → cleanup → done，
不代表新闻等正式业务模块已经接入。

## 权限边界

sync_grants 保存主体、范围、读写/删除能力、有效期与修订令牌。
可信的宿主授权服务通过 put_grant 更新；任何修改都会生成新修订，阻止旧任务继续提交。
每次数据库提交再次查询当前授权和对端修订，而非只信任领取时的 Python 快照。

任务命令方法属于内部 API。网站必须先认证用户，再把该用户可操作的 grant_id 交给仓储；
绝不能将浏览器传入的任意 grant_id 或 can_write 当作认证结果。
实际网站的密码、角色和账号修改事件还没有挂接；第五/六步须维护这些授权修订。
未接入这层之前，不可将本模块直接暴露为公共 API。

pause/cancel 不清除有效租约，但任务状态会立即使旧提交失效。
lease 到期前不能 resume；权限变化后的继续会撤销旧写入确认，要求重新确认。
对端修订变化要求新建预览，不把原范围默默应用到新的对端。
取消后只清理暂存，已经写入的业务记录保留；未知归属文件的处理留给第四步媒体适配。

## 提交和恢复

全站领取守卫确保同一时刻只有一个有效同步租约。各轮独立生成 attempt_id。
业务 SQL 与条目 applied 标记、progress_seq 在同一数据库批次提交。
业务处理器提交单条参数化写入，并在 WHERE 中检查目标版本；若没有恰好影响一条记录，
事务回滚并报告冲突。条目已 applied 时重放不再次执行业务 SQL。
实际应用模块提供的 SQL 是可信服务端实现，不得接受对端直接提供的 SQL。

收到异常或发现过期运行标记时，以 attempt_start_seq 与当前 progress_seq 判断进度：
有进度则连续无进展清零，累计异常仍保留；没有进度按配置退避，再转长期低频恢复。
无整个任务的总时限。正常成功但无进度既不重置无进展计数，也不消耗失败额度。
资源异常会缩小正文切片；即使有进度，也至少等待 Worker 60 秒/本地 5 秒，避免快速重复超限。
资源异常后的媒体 part 调整不在本步实现，仍遵循 R2 的存储分段限制。

永久授权错误/明确冲突暂停；未知暂时错误进入退避。ResourceError 由后续传输层在确认
资源错误时使用；本步没有将所有 1101 自动等同于资源超限。
进程被强制终止后不会运行 finally 或虚构回执，保留运行标记等待下一轮核对。
同一次尝试最多核对计错一次，过期令牌不能覆盖新轮状态。

## 数据库升级

结构版本由 1 升到 2，单一 schema.sql 同时供新库使用。
历史 schema_v1.json 仅保存第二步结构指纹，不是第二份初始化 SQL。
自动迁移添加字段和授权表，保留任务、正文暂存、条目和媒体进度；
未结束旧任务暂停并禁用旧授权，不虚构原任务归属或自动批准。
可信管理员服务可用 bind_upgraded_task 绑定新的有效授权，随后按原范围重新确认。
迁移失败保持旧版本；已有数据的升级要求可恢复备份。
此迁移只支持本轮第二步的新数据库，不宣称支持任何旧网站数据库格式。

## 本地验证和限制

执行 python -m site_sync.tests.verify 可重跑数据库、执行器、第一步恢复模型和 Node 流测试，
并运行完整流程示例及初始化/重复部署/检查/D1 计划生成 CLI。
实际结果见 step3-results.json。

覆盖同时领取、暂停/取消时旧令牌、授权撤销、确认重放、目标写入冲突、业务提交后丢回执、
强制终止、清理后完成，以及连续 40 次有进展资源异常。
SQLite 是真实本地数据库；D1 仍使用 SQLite 支撑的 binding 替身，不模拟真实 Cloudflare、
Pyodide 桥接、CPU 或内存配额。示例使用虚拟时钟，不执行网络同步。
生产 Cron、本地服务、网站账号/角色事件、真实两端 HTTP 和 R2 均尚未挂接。
