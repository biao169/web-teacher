# v0.15.139：第六步——统一低负载同步验收

日期：2026-10-03。此文为v133—v138这轮六步改造的当前验收入口，媒体规则以v137为准，替代v131中“同步删除旧媒体”的历史描述。

## 结论范围

本包包含本地可执行验收、跨平台适配器矩阵和部署后操作清单。结果记录在 `site-sync-acceptance-v139.json`。

测试中的本地SQLite/文件为真实实现；Worker组合使用项目的D1SQL、R2Store和R2Inventory，以临时SQLite和内存对象模拟远程绑定。**不是实际Cloudflare Worker/Pyodide运行，也不是Windows或Ubuntu/Debian实机部署验收。** 未访问生产网站、使用线上密钥、更新GitHub、部署服务或更改云端数据库。

## 六步实现与验收对应

| 步骤 | 已有实现 | 验证内容 |
| --- | --- | --- |
| 统一基础 | 共用低负载策略、任务锁、持久检查点 | 浏览器/后台互斥，失败记录、运行中断后的继续 |
| 分页读取 | 内容5条/普通页64KiB，版本20条，稳定游标摘要 | 长记录独页、超限停止、分页变化后无遗漏及重复 |
| 分批分析 | 引用及差异逐条，删除依赖5项 | 与共用比较器一致、主键范围查询、事务失败回滚 |
| 分批执行 | 逐条规范化/关联校验，64KiB下载，4路流合并、4对象清理 | 先新媒体后引用；目标旧媒体保留；摘要/版本错误不发布；提交ACK丢失不重复提交 |
| 恢复交互 | 继续、取消、幂等重新开始，2/5/15秒有界重试 | 暂时错误3次重试，永久错误停止，暂停可中止等待，旧批准不继承 |
| 本轮验收 | SQLite↔模拟D1/R2、模拟Worker↔Worker，界面及部署回归 | 提案最新版本、延迟批准、事务回滚、媒体版本变化、手动真实删除、部署跳过源码校验 |

手动继续将内容页降为1条、版本页降为5条，不改变已保存游标或摘要算法。

## 内存专项

新增 `tests/test_sync_acceptance_v139.py` 对本地1MiB、20MiB文件执行流式复制与SHA-256校验，使用tracemalloc验证该操作的Python分配峰值低于1MiB，并确认无残留临时文件。具体测量值写入JSON。

这些数据仅覆盖本地流式函数的Python分配，不包括操作系统页缓存、全部网站内存、R2模拟对象或真实Worker JS/WASM堆，不能换算成生产CPU上限。最后业务提交仍是原子事务，最后版本/媒体检查仍集中执行；不能据此宣称1101/1102全部消失。

## 两站部署后验收（待执行）

无需重置数据库，协议仍为7、任务格式仍为8，可继续v137/v138任务。建议先关闭后台自动同步，在两端部署同一完整版本；遵循各部署方式原有更新流程，不初始化有数据的库。不要同时两端编辑或同时开启相反方向的自动拉取。

| 顺序 | 操作 | 通过标准 |
| --- | --- | --- |
| 1 | 双向测试连接 | 签名、协议和身份通过；这一步不代替内容同步检查 |
| 2 | 在A创建专用验收教师/学生/新闻及小图片，B拉取 | 只写入选中内容及依赖，字段和媒体显示正确 |
| 3 | A将内容引用从a改为b并在A手动彻底删除a，B同步内容更新 | b先可用，引用改为b；B的a登记和真实文件保留，无媒体删除差异 |
| 4 | A媒体登记存在但实际文件丢失 | 同步停止并显示阶段；不提交失效引用；恢复原文件后可继续，若内容/版本变化则重新预览 |
| 5 | 同步选中的专用非媒体条目删除 | 只删除已选业务条目及必要依赖，不顺带删除媒体 |
| 6 | 暂停、关闭页面、重新登录后打开原任务 | 游标继续；既有提交不重复，已保存分片不从头重传 |
| 7 | 注入短暂网络故障后恢复 | 错误可见；有限退避；超过上限停止，手动继续可恢复 |
| 8 | 重新开始与取消 | 清理未登记的本任务暂存；已提交内容不回滚；新预览需重新勾选确认；重复重启不生成重复新任务 |
| 9 | A连续发送两份不同推送提案，B稍后审批 | 只核对最新提案，旧审批不可执行；未批准不修改业务数据 |
| 10 | 反向B→A重复小规模同步 | 使用同一流程；由于无删除墓碑，B保留媒体可能成为对A的新增候选，可不勾选 |
| 11 | 仅接收站开启后台推进 | 每轮推进小步骤，失败按策略等待或暂停，不偷偷新建替代任务；关闭策略停止后续推进 |
| 12 | 在目标站媒体库清理专用验收媒体 | 先解除引用；手动彻底删除同时删除登记及真实磁盘/R2对象 |

首次先用小数据，再测试1MiB、接近20MiB媒体，以及较多条目。当前单文件20MiB、每任务100媒体/总计24MiB、实际变更500项等边界仍保留，不为验收扩大限制。

### 线上性能和错误记录

在Cloudflare日志中记录每次实际异常的路径、阶段、Ray ID、诊断编号、CPU/墙钟时间及数据规模；Ubuntu侧记录同一任务阶段及应用日志。不要提交密钥、Cookie、账号密码或完整私密正文。

- 进入同步页就1102：检查启动/渲染和首次加载；不要误认为是数据推进速度。
- advance超限：记录当前读取/分析阶段及单条正文规模。
- pull-tick超限：区分下载、合并、校验、最终提交或清理；重试不能修复确定性的单步超限。
- 409内容变化：重新核对预览；不关闭事务保护来强行覆盖。
- 500/502：提供具体错误码和对端日志；不通过重置业务数据库或删除R2桶排障。
