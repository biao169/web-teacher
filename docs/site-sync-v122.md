# 两站同步第三步：v0.15.122

本版增加“本站 → 对端”的提案发送、接收方重新预览、批准/拒绝和执行回执。批准后的任务复用 v121 的拉取执行器，不另建一套媒体上传、引用更新或删除流程。

## 使用步骤

1. **两站更新到 v0.15.122。** 保留原共享密钥和对端地址。
2. 在接收方“数据与备份 → 两站同步预览”的连接配置中勾选 **接收对端的待批准推送**，保存。此开关默认关闭；只启用业务读取不会允许接收提案。
3. 发起方生成“本站 → 对端”预览，勾选条目，点击“发送 / 重试发送提案”。这里只向对端保存范围与选择，不写业务记录或媒体。
4. 接收方打开相同页面，在“接收到的推送提案”点击“重新读取最新差异并核对”。无需使用发起时的登录会话，也不受短会话凭据有效期限制。
5. 核对最新的新增/更新/删除清单和媒体依赖，可减少本次选择。输入 **同意对端推送**，点击“同意并执行最新差异”。也可直接拒绝当前提案。
6. 执行期间沿用阶段进度、暂停、继续/重试、取消清理。发起方可以打开原预览，点击“查询对端审批与进度”查看回执。

保存连接设置会使既有预览失效。首次开启接收功能后再生成发送预览；后续改地址、密钥或开关时，先处理未完成任务，再重新生成预览或提交新版提案。

## 多次发起如何处理

同一个方向只保留一个当前提案，使用持久化递增序号区分新旧。

- 第一次选 X、Y，第二次选 Y、Z：尚未批准时，当前选择变为 **Y、Z**，不累加成 X、Y、Z。
- 新提案到达后，旧的审批预览不能再用于批准。接收方需打开最新提案重新核对。
- 已批准任务拥有自己的固定选择与执行进度。新提案独立等待批准，不覆盖已经运行的任务。
- 延迟到达或重复发送的旧序号不能恢复旧选择；已拒绝的同一提案重发也不会重新变为待批准。
- 发送回执丢失时，重试沿用原提案序号及标识，避免重复产生请求。已确认送达后再次主动点击发送，则产生新版提案。
- 保存最近20条简要历史回执，不保存无限增长的旧选择副本。更早回执可能显示“不在保留范围”；当前待批准提案持续保留。

## 等待很久后批准

提案保存的是条目标识和范围，**不是等待数周后原样执行的一组旧 SQL**。接收方重新预览时读取两站当前数据：

- 已选条目后来改名或更新：展示最新内容的差异。
- 原选择已经一致或不再需要操作：从当前清单去掉，并显示数量。
- 原选择对应条目现在需要删除：以当前删除差异明确展示，再由接收方批准。
- 来源新增、但未在本次提案选择中的独立条目：不会自动混入；只有必要依赖随当前选择加入。
- 媒体替换关系变化：重新计算当前引用和新媒体依赖，不使用过时的依赖清单。
- 当前已完全一致：可确认该提案无需执行，不修改业务数据。

批准前和实际提交前仍重新验证两站数据版本。审批预览后又发生编辑，会停止旧任务，要求重新核对。已批准任务也不会因为新的提案而放宽版本检查。

## 权限、审批与存储

签名对端接口新增的写操作仅限固定的提案收件箱元数据；不开放任意 SQL、审批、业务修改或媒体删除操作。接收方必须明确开启提案接收，并验证请求来源是已配置的对端。

批准与任务创建在同一个数据库批事务中，校验当前提案和审批预览仍匹配；新提案先到达时，旧审批不能穿过此检查。批准入口继续要求本地管理员身份、模块权限和 CSRF 验证。提案传输签名仍验证当前请求时间，但保存在数据库中的待批准提案没有短会话有效期。

收到/等待提案不上传媒体。只有接收方确认后才沿用 v121 流程：先校验媒体 → 原子提交内容/引用 → 复核并删除旧媒体。暂存、取消、不覆盖同名不同内容、文件大小及变更项数量限制均保持 v121 的行为。

## 数据库与部署

**表结构与 v0.15.120 / v0.15.121 完全一致，不需要迁移或重建，不新增依赖和端口。**

复用 `service_meta` 保存开关、收件箱、序号和最近回执；复用 `sync_tasks.state` 保存发送记录、审批预览关联和执行进度。这些内部状态不进入业务同步范围。已有连接配置保留，接收提案功能需手动开启。

从 v119 直接升级仍按 [v120 说明](site-sync-v120.md) 补齐三张内部表；不要通过 reset 清空数据。
