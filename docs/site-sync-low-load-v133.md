# v0.15.133：统一低负载同步——第一步

本步完成统一配置、任务状态、检查点和同任务互斥。Worker与Ubuntu/Debian共用相同方法，不按平台使用不同算法。不是六步改造的全部完成，也未证明线上1102已经消除。

## 已生效的配置

集中在 `backend/app/native/site_sync_work.py`：

| 项目 | 默认值 | 本步行为 |
|---|---|---|
| 内容记录 | 每批最多5条 | 两端查询和响应校验共用；此前为20条 |
| 浏览器批次间隔 | 1000毫秒 | 预览、确认、推送和执行请求串行等待；等待期间可暂停 |
| 媒体分片 | 64KiB | 共用区间大小；此前为256KiB |
| 暂存清理 | 每批最多4片 | 清理游标保留，后续步骤继续 |
| 单页正文 | 1MiB上限 | 沿用现有拒绝过大页面的检查，尚未实现动态字节分页 |
| 单记录 | 200000字节字段预检 | 沿用原限制，不会跳过超限记录后推断删除 |
| 版本页 | 100条 | 暂不改变摘要分片边界；下一步一起改造稳定摘要 |

后台仍每次调度推进一个步骤，使用原本更长的调度间隔。浏览器等待发生在两次HTTP请求之间，不在Worker内部空等。没有无限重试或宣称通过等待提升CPU上限。

原有总量约束继续适用：最多2000条/站、预览总内容4MiB、单任务实际选择最多500项、单媒体20MiB、媒体合计24MiB。媒体最终合并和最终差异比较仍可能较重，后续步骤继续拆分。

## 任务与恢复

- 复用 `sync_tasks.state` 存放策略快照和小型工作状态；业务游标、来源版本和暂存位置沿用现有字段。数据库表及SQL不变。
- 步骤开始先保存操作、阶段、尝试次数、开始时间；完成后保存最后完成时间及步骤计数。已处理条数与表位置可查询。
- 工作状态使用数据库JSON局部更新，不额外在Python中读取、序列化整份任务来写入这些元信息。它仍增加少量有界读写，以换取可定位和恢复的检查点。
- 普通异常保存阶段、错误分类和现有诊断信息，保留原游标。修复问题后打开最近预览/任务继续。
- 1102可能直接终止Worker，错误处理代码不一定执行。已保存的“处理中”和上一成功游标仍保留。不要把“处理中”视为完成；重新打开任务检查。异常终止遗留的租约按现有规则最多保留约5分钟，过期后可继续；不会同时启动第二个执行者。
- 预览、选择、确认执行、实际推进、提案发送与审批预览收尾共用任务租约。SQLite和D1重复租约统一返回可恢复的409提示。不同任务仍可独立工作；本步没有提供跨站分布式事务。
- 后台预览失败保留原 `preview_uid`，不再丢弃后自动重建；等待手动打开原预览重试。浏览器继续和后台推进调用同一套方法，租约忙时后台跳过本轮。
- 普通历史预览清理不再删除仍在读取、暂停或处理中任务。原有“最近预览”入口用于恢复；专门的重新开始/取消界面将在第五步完善。

重新开始仍可使用现有方向按钮新建预览。已开始的实际执行任务先继续或取消，新预览不会撤销已经提交的数据。取消清理及媒体引用保护沿用原方法。

## 更新要求

协议升级为5，任务格式升级为4。两端同时更新本步相关功能文件；不能一端v133另一端v132。升级前暂停定时同步，完成或取消旧的实际执行任务。旧预览在新版明确提示重新生成，不转换旧游标、不重置数据库。

已经升级但仍有未结束的旧执行任务，应先用对应旧版完成或取消再升级，不要删业务记录处理任务问题。启用定时同步前先通过新协议连接测试并生成新预览。

v132的部署跳过源码完整性校验保持生效。发布清单不影响部署，但本步新增模块与调用它的文件应一起更新，避免仅上传其中一个文件造成导入错误。
