# v0.16.034 · 稳定性专项第五步：单步工作量与持久断点

仅基于本分支 v0.16.033-isolation-step4。没有修改三种同步业务模式、数据库结构或已有任务。仍只有 `database/schema.sql` 一个初始化 SQL。

## 本轮改动

| 阶段 | 当前单次工作与持久状态 |
| --- | --- |
| 普通候选发现 | 一次读取一个候选；记录、进度计数和 discovery_cursor 在同一数据库事务提交 |
| 克隆候选发现 | 同样原子提交候选和游标；远端跨表查找改成一次 SQL，每张固定业务表最多贡献一个键，再由数据库选出一项，避免在 Python 中连续请求多个空表 |
| 清单 | 获取并保存一个有上限的 manifest 后结束，不同时登记全部媒体 |
| 媒体登记 | 从已固定的 manifest 查找下一个未登记文件，一次只新增一条 sync_files，再结束；不会同时下载正文或媒体 |
| 正文 | 保持一次只下载并提交一个分片；日志增加字段、偏移及分片大小 |
| 媒体传输 | 保持一次一个既有媒体步骤，使用持久回执恢复；不改为一次传完整个文件 |
| 克隆暂存 | 保持一次整理一条业务记录 |
| 克隆校验 | 拆成清单范围校验 → 逐表数量检查 → 对端版本检查 → 管理员与应用锁检查；每一步保存阶段和表索引后返回 |
| 恢复 / 清理 | 保留原来逐条记录、逐个分片的处理方式；未知克隆 checkpoint 阶段明确报错，不再意外进入清理 |

普通同步仍最多选取最新 500 个候选，由数据库排序并逐项返回，不会把全量历史记录读到 Worker 后再截取。已有整站/分项克隆需要完整清单，其总量不在第 500 项截断，否则无法兑现完整克隆；它仍逐项读取，不在内存中保存完整清单。此处保留上一版已存在的业务规则。

## 中断恢复

候选插入、progress_seq 和 discovery_cursor 现在在同一事务内：提交前失败全部回滚；提交成功但应答丢失时，重试不重复累计候选进度。游标提交检查旧断点，过期的重放不能把已经前进的游标退回。

manifest 先持久保存；媒体登记根据已保存的 sync_files 恢复，不依赖前一次运行时对象或全局文件列表。每次只增加一个描述项，插入和进度更新同事务；应答丢失后不会重复创建文件或重复计算进度。

克隆使用原有 `service_meta / sync:clone-state:<task_id>` 保存 `verify_tables`、`verify_source`、`verify_admin` 等子阶段。逐表检查完成后记录下一表索引；即使本次调用随后异常或模拟硬终止，租约恢复后仍从下一表继续，不重新检查已成功的所有表。有持久进度时沿用现有规则，不累计连续无进度失败。

没有增加逐片人工审核。原有一次任务批准、自动确认、签名鉴权、权限与租约校验继续保留。

## 诊断与后台

- 步骤日志增加 `candidate-page`、`fetch-manifest`、`register-media`、`download-body-slice`、`media-step`、各克隆子阶段名称。
- 在请求局部上下文中记录当前记录、媒体、偏移；退出仍由原有 ContextVar scope reset，不保存同步进度到全局内存。
- `sync_events.detail.clone_checkpoint` 从数据库读取已提交的克隆断点，不将仅在内存中计算的位置当成持久成功；无效或过长的状态 JSON 不注入日志。
- 后台显示逐表检查进度、当前表及新增子阶段，诊断卡显示克隆子阶段断点。查看这些信息不会推进任务。

## 保留的原子边界与限制

账号、角色、权限的最终替换仍在一个有既有 1000 行上限的事务中完成，避免半套账号导致锁死后台。关联媒体键的数据库更新也保持其原有事务一致性。本轮未将这些安全边界拆成不完整的业务写入。

对端清单摘要仍由数据库聚合生成；单条记录的 SQL 封装、最终账号事务、媒体键引用更新仍可能是较重的数据库操作。本轮不宣称每条 SQL 恒定耗时，也未实测线上 CPU/内存峰值。正文切片仍允许 4 KiB 至 4 MiB 配置；单条正文和 manifest 保留既有上限，R2 继续使用原来的原生流式媒体分段机制。
