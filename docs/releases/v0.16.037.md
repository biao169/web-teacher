# v0.16.037 · 修复打包后 executor 资源隔离失败

仅基于本分支 v0.16.036-isolation-step7。没有修改同步模式、最新 500 项候选规则、签名、审核、任务 ID、checkpoint、媒体协议、业务数据库或前端页面。

## 根因已复现

原版在真实 PACKAGE 后 staging 中运行 `startup_check.py --executor-only`，可稳定复现：

```text
AssertionError: Executor loaded website runtime: generated_resources
```

独立 import 探针确认，第一个直接导入该生成模块的是 `backend.app.native.catalog`。实际路径：

1. `worker_runtime.sync_executor` → `worker_runtime.sync_resources` → `backend.app.adapters.d1.sql` → `backend.app.native.catalog` → `generated_resources`。
2. 同一 `sync_resources` → `site_sync.integration.peer_api` → `site_sync.integration.host` → `site_sync.integration.catalog` → `backend.app.native.catalog`。第二条会复用 Python 已加载的模块，但如果只删除第一条，仍会触发该依赖。
3. 实际同步/克隆业务还使用共享 catalog，例如 `site_sync.integration.website` 依赖同步 catalog，`site_sync.integration.clone` 使用共享 TABLES；所以只延迟顶层 import 也不足以解决运行时耦合。

这不是本次日志证明的线上 1101/1102，也不是平台冻结：它是在上传之前由主机上的隔离断言主动阻止部署。

## 为什么之前测试漏掉

源码目录没有 `generated_resources.py`，catalog 会读取 `database/native/*.json` 的 fallback，因此源码 executor-only 测试不会见到被禁止的生成模块。

旧离线 staging 脚本虽然创建了真实生成资源，却只执行普通主站检查。在该检查中主站先预加载网站模块，executor-only 禁止模块断言并不运行。真实部署 pipeline 额外开启了独立进程 EXECUTOR-SNAPSHOT-CHECK，因此暴露了遗漏。上一版“离线打包通过”并不等于独立执行器在真实 staging 中通过，此次已补齐。

## 资源拆分

`deploy/shared/worker_package.py` 在 PACKAGE 阶段生成文件；`deploy/cloudflare/pipeline.py` 将两份资源一起移动到 `stage/src/`。`integration_package.extend()` 随后只向网站资源文件追加快传资源。

| 最终生成文件/内容 | UTF-8 源文件或 repr 大小 |
| --- | ---: |
| 修复前 generated_resources.py 整体 | 514,513 字节 |
| 修复后 generated_native_resources.py 整体，仅 NATIVE | 162,776 字节 |
| 修复后 generated_resources.py 整体 | 351,737 字节 |
| 网站文件内 TEMPLATES 的 repr | 246,704 字节 |
| TRANSFER_TEMPLATES 的 repr | 48,126 字节 |
| TRANSFER_DEFAULTS 的 repr | 1,726 字节 |
| TRANSFER_CATALOG 的 repr | 55,104 字节 |

repr 数值不包含变量名、分隔符等，因此与文件整体大小略有差别。生成模块不是源仓库中的固定文件，由部署时动态生成，不应手工上传旧生成结果。

同步业务真正需要 schema-spec 中的表结构、字段与共享 catalog 规则。为避免本轮过度拆分，保留共享 catalog 的 editor-contract 数据；它们进入独立 native 模块，不再携带网站/后台/快传模板。打包校验会检查 native 内容与规范源完全一致，并拒绝把 NATIVE 再合回网站文件。

## 执行器现在如何加载

- 顶层只保留 WorkerEntrypoint、请求诊断等轻量声明，不导入 peer application、Starlette 或网站 catalog。
- `scheduled()` / `sync_tick()` 使用 `site_sync.adapters.d1.D1`。检查了调用接口：调度直接使用 query/binding，同步事务经 integration.database 的适配器执行，不依赖网站 D1SQL 的 Error 包装、restore_batch 或返回形状。
- 有到期任务才按原有流程加载 host/业务映射和 native catalog；不提前构造网站 application。
- 仅非媒体的 `fetch()` 路径按需导入 workers.asgi 与 `sync_resources.application`。它是同步专用 HTTP 入口，不是完整网站应用。媒体继续原样转发到原生辅助服务。
- `sync_resources` 也改用同步自己的 D1 适配器。
- 不删除任何隔离门禁。`generated_resources`、`backend.app.native.web`、`worker_runtime.resources`、`worker_runtime.transfer`、`backend.entrypoints.worker` 仍禁止进入 executor 依赖图。
- 检查另行禁止 executor 冷启动加载 peer HTTP 和 catalog，并检查 Cron 的延迟依赖不能带入 Starlette/peer API。

本地相同解释器下的轻量导入观测：

| 场景 | sys.modules 总数 | 项目模块数 | 生成资源 |
| --- | ---: | ---: | --- |
| 原版打包后 executor 导入探针 | 269 | 46 | 综合 generated_resources，隔离违规 |
| 修复后 executor 冷启动 | 196 | 8 | 无 |
| 修复后按需同步 + peer HTTP 依赖检查 | 265 | 42 | 仅 generated_native_resources |

冷启动不加载 backend；按需业务依赖仍包含 `backend`、`backend.app`、`backend.app.native`、`backend.app.native.catalog` 四个共享命名空间/模块。它们不是完整网站 runtime。没有把必要的共享业务定义复制成第二套实现。

以上为 CPython 模块数量和源文件字节数，不是 Pyodide 堆内存、Worker CPU 或 snapshot 大小实测。后续若实测 catalog 仍是明显热点，可再单独评估 schema 与 editor-contract 的拆分；本轮不扩大改动范围。

## 测试与诊断

生产部署保留 `SNAPSHOT-CHECK` 和 `EXECUTOR-SNAPSHOT-CHECK`，新增 `EXECUTOR-DEPENDENCY-CHECK`。三个检查在各自独立进程运行，均在 SDK 构建/上传前执行。

新增 `deploy/cloudflare/tests/test_staged_executor.py`：使用真实 prepare + extend，生成两份模块，复制至实际 stage/src，在 staging 工作目录执行主站、冷启动、延迟依赖检查。负向测试把网站 import 注入 native 模块，确认仍被拦截；移走 native 文件也必须失败，不能偷偷借源码 JSON fallback 通过。

`tests/stage_release_v016001.py` 同样增加 staged executor 两项检查，inline/separate 两种离线打包都执行，输出模块与资源信息。原有源码 startup check 继续执行，命令使用 `python -B`，与部署流程一致，以避免 Python 自身写 pyc 触发禁止写入的审计。

隔离错误现在包含 separate 模式、所有被禁止模块及实际文件路径、允许的 native 模块，以及资源生成检查提示；没有加入运行时 import tracing 框架。仅本次离线原版探针用于确认首个导入者，不随交付发布。

验证通过：Python 全量 641 项、47 项子测试；1 项仅适用于 D1 的应答丢失测试在 SQLite 参数下跳过，D1 分支通过。额外资源/域名测试 21 项通过；强化后的源码/真实 staging 隔离测试 16 项通过。inline 与 separate 离线打包三个启动门禁均通过。尚未执行真实 workers-runtime-sdk / Pyodide bundle、线上发布或 D1/R2 额度验收。日志中的本次确定故障已在实际生成资源的 staging 条件下复现并消除。
