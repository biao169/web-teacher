# v0.16.112 — 第四步：模块级缓存维护

基线v0.16.111，未部署线上、未执行生产purge。

## 接口与权限

新增POST /api/admin/public-cache/reset，只接受module和既有_csrf。模块白名单：home、profiles、students、projects、publications、patents、courses、news、research_interests。不接受任意tag、URL、action或purgeEverything。

复用实时resources鉴权、同源CSRF、维护系统角色要求，另需global_settings删除权限；密码待更改、普通用户、会话撤销或权限撤销均不可操作。返回始终no-store。常规授权/会话心跳仍走原流程；维护不读取公开内容、不改公开数据或新增任务。

## 复用原缓存链路

受保护Admin接口在Worker中返回202内部待处理标记。原SITE_ADMIN私有转发之后，由main Default验证模块，复用既有Plan与PublicPage/PublicData.update_public_cache RPC，分别在所属entrypoint执行同一个模块tag的purge。原Admin entrypoint已有响应透传即可使用，不新增Worker、绑定、Token或Cron。

每个RPC只调用一次、最多等待3秒，两边并行且独立收集结果。平台true为accepted，明确false为failed，异常或超时保守记unknown，因为无法断定操作是否被平台接受。全部接受返回200；明确拒绝返回502，未知结果返回503；包含module、page_cache、data_cache、request_id及失败code。结果在原Admin恢复边界之后生成，避免部分失败JSON被通用恢复响应覆盖。普通提交通知仍在原位置执行，不改变成功保存、回滚、invalidate/purge分类及pending处理。

模块级purge包含对应tag的中英文列表和详情，不能删除未带该tag的对象。首页只使用public-home Page标签，data_cache为not_applicable，不假报清理JSON；其他模块操作不顺带全站或首页purge。Ubuntu/Debian返回两项not_applicable，不引入本地缓存。

日志记录module、cache_tag、Page/Data结果和request_id。内部控制头不返回给客户端，待处理JSON流被取消而不解析、缓冲或重放。没有自动重试、全站purge、后台任务、扫描、预热或公开页面请求。正常公开修改继续原invalidate规则，公开撤回仍保持原精确purge规则。

## 管理界面

后台“运行维护”增加“公开缓存”，九个模块各有“清除异常缓存”按钮。点击前确认，期间防重复提交，分别显示页面和数据结果。页面加载不会发缓存维护请求，超时或错误不重试。单服务只显示不适用说明。

平台接受不等同于已观察到全球对象删除。清理不删除浏览器已有新鲜缓存或已加载Read Model；也不能修复页面生成500。清理后下一次真实访问自然MISS，若仍500应检查页面生成和平台日志，不要循环清理。purge将移除对应旧成功对象的stale回退能力。
