# v0.16.031 · 稳定性专项第二步：请求资源归属与异常清理

基于本分支 v0.16.030-isolation-step1。没有修改业务规则、数据库表或已有任务数据；仅保留 `database/schema.sql`。

## 修改

- 原生传输删除模块级 `responseCleanup` WeakMap。清理回调现在使用不可枚举 Symbol 属性挂在当前 Response 上，释放后删除属性；模块只保存不变的 Symbol 标识，不保存响应集合、任务或正文。
- 清理回调幂等；非流式请求成功或异常结束时释放计时器并中止请求控制器。流式请求由消费方完成或失败时释放；未完成传输仍保留原有超时保护。
- 对超时后才到达的流响应、清理归属交接失败、reader 异常及 R2 上传异常补齐清理路径。
- 保留原始 Response 和原生 body，不包装成新的 ReadableStream，避免丢失原生流属性，不将媒体整体读入内存。
- 清理异常记录 `SYNC_CLEANUP_FAILED`、安全异常类型和清理阶段，不输出原始异常正文；优先保留最初的传输/鉴权错误。
- 原生诊断代码集合改为冻结的只读接口，固定字典不会在请求中增长。
- Ubuntu/Debian 及 Windows 同步 HTTP 连接改为单次释放；媒体响应关闭失败时仍继续关闭连接。关闭失败记录异常类型，不覆盖最初的读写错误。

WeakMap 本身不等于内存泄漏，本次没有证据认定它是线上 1101/1102 的根因。修改目的是明确资源归属、缩短异常路径上的引用生命周期。

## 状态审查与保留决定

| 对象 | 归属与结论 |
| --- | --- |
| 原生 Response 清理登记 | 删除全局 WeakMap，改为当前响应拥有回调 |
| AbortController / timer / reader / HTTP 连接 | 当前调用拥有；成功、错误、超时、上传失败均有清理路径 |
| 当前任务、候选、manifest、正文 | 现有 Runtime/步骤局部对象；未发现全局任务列表或正文下载缓存，不改为全局缓存 |
| sync_tasks / sync_items / sync_parts / sync_file_parts、克隆 checkpoint | 保持数据库持久状态；本轮不清除、不重建任务 |
| LazyApplication | 保留完整构建后才发布的应用引用；失败构建不发布半成品，不保存当前任务。单次请求错误不清空整个应用 |
| Jinja 模板缓存 | 保留 WorkerBudget 的 24 项模板 LRU；只缓存模板，不存用户上下文或同步正文 |
| RequestSQL | 保留请求内缓存：64 KiB 总预算、16 KiB 单项、最多 32 项；同步、service_meta、账号等查询绕过缓存 |
| Environment / D1 / R2 包装 | 请求或 tick 内创建，不将绑定、用户或对端密钥挂到模块级对象 |
| 表结构、权限字段、错误码、标签定义 | 固定大小定义；不作为任务容器使用 |
| SQL 诊断 ContextVar | 上下文局部槽位，默认 None；当前同步路径不向其保存任务状态 |
| 协调器失败次数与 Alarm | 持久存储；不搬到 isolate 全局内存 |

未改变网站路由、前台样式、业务账号功能或同步模式。模板容量与请求缓存原本已有上限，本轮不重复重写。

## 验证

- Python 全量回归 571 项及 47 项子测试通过；随后 HTTP 单次释放修改与新增案例的 78 项定向回归通过。
- 原生 JS 47 项通过，覆盖超时、异常控制器释放、两个响应相互隔离、重复释放、鉴权错误不被清理错误覆盖。
- workerd 原生传输测试通过，验证 Response 清理属性可使用且流式签名传输正常。
- inline / separate 离线打包与启动导入检查通过。
- 增加应用异常测试：一次请求抛错后，下一次仍能使用原应用；应用对象不增加 task、request 或 checkpoint 字段。

未进行线上发布、真实 CPU/内存峰值测量或 PoP 对照验收。平台强制终止时不能保证执行 finally；恢复仍依赖数据库断点和租约，不能把清理函数当作强制重启 isolate 的手段。
