# v0.16.044：统一同步目录与接收创建入口（修复第一步）

基于本分支 v0.16.043-acceptance-step6。未发布到线上、未修改生产数据。

## 使用方法

两端更新完整源码，保留原数据库、媒体和部署配置。Ubuntu 与 Worker 的同步页面、参数控件、目录说明仍共用 `site_sync/frontend/templates/` 和 `site_sync/frontend/static/`。

1. 使用连接所属的系统管理员打开 `/admin/site-sync`。
2. 新建任务和计划固定显示 20 个 `restore_*` 项目。旧授权中的12项不会再改变卡片目录；尚未授权的项目禁用，并显示原因。
3. 若提示“本站保存的同步授权尚未更新”，点击“更新同步授权”，确认按当前管理员权限补齐本站同步及导出范围。Ubuntu 和 Worker 各自保存授权；只更新一端不会改变另一端。
4. 页面重新载入后，核对媒体、账号、角色、权限卡片可选；再测试对端连接、继续原等待任务或创建新任务。

更新授权是显式 POST 操作，必须通过会话、CSRF、系统管理员、连接归属、有效授权和事务内状态校验。不接受客户端自定义授权范围。仅补齐当前账号实际拥有的权限；权限已经收缩、连接停用或过期时拒绝更新，需通过连接设置处理。

安全扩展不会更改已有任务/计划的范围、断点、任务修订号、授权修订号或接收自动审核策略。旧任务保持原来的12项业务范围，新任务从20项分项目录选择。若原任务只是因对端缺少恢复范围而等待，更新对端导出授权后可继续按原有重试机制推进。

## HTTP 400 定位

新增 `SYNC_INPUT_INVALID`，返回 `field`、`expected`、`stage`、`error_type`、`request_id` 和 `retryable=false`，界面同时显示字段、要求及追踪ID。日志关联同一请求ID，不回显任意请求正文或密钥。

可识别：混用 `news` 与 `restore_news`、空范围、确认开关类型错误、自动恢复未允许替换、参数覆盖不是对象、切片低于4KiB或超过4MiB、最小切片大于初始切片、重试参数超出范围等。

例如选择分项恢复并启用自动确认，但取消“允许替换/删除”，返回 `field=auto_delete`；可勾选许可，或关闭自动确认、后续人工审核。输入 `4m` 合法，对应4MiB。

此前追踪 `15499cc2c529e11a1d9d722e52ce2868` 没有原始请求参数和对应服务端日志，不能断言当时具体是哪一个字段触发400。本轮补齐的是可复现参数分支与诊断机制，下一次错误可准确定位。

## 共同接收入口

新增 `site_sync/core/receiver.py`，手动拉取、推送提案接收、定时拉取统一经过 `create_receiver()` 校验范围及确认策略，再调用原有持久化任务创建逻辑。依赖归一化、权限检查、幂等标识、调度排他与断点处理继续保留。

手动拉取默认自动确认；推送仍由接收端已保存策略决定是否审核；定时拉取自动确认。没有为了绕过403而移除签名或导出授权，也不让普通页面推进任务。
