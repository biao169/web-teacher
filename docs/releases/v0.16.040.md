# v0.16.040 · 第三步：持久上传会话与残留恢复

基于本分支 v0.16.039。继续原生流式上传，在现有 service_meta 中加入有期限的上传会话。数据库结构及唯一初始化 SQL 不变，不需要手动执行 SQL；不改同步模式、任务数据、业务页面和后台布局。

## 上传状态与登记安全

上传占用锁和 receiving 会话在同一个数据库事务写入。会话保存上传 ID、随机对象键、锁所有者、创建/到期时间、状态和原请求 ID，不保存文件正文。原生辅助 Worker 在消费文件流前读取会话，拒绝缺失、重复已存储、对象不匹配或到期的会话。

文件仍按最多 64 KiB 顺序流式读取并计算摘要。R2 写入后，辅助 Worker 条件更新会话为 stored，记录字节数、MIME 和摘要；若会话已到期或被移除，拒绝成功回执并尝试删除迟到的对象。

主站最终登记事务再次要求会话为 stored 且未到期。媒体记录、审计和会话删除处于同一事务。没有正文持久化到 isolate，也不依赖内存恢复上传进度。

如果数据库已提交，但请求未收到确认，失败清理会先检查媒体表；已登记对象保留，不会因为 committed 内存变量仍为 false 就删除文件。若数据库本身不可查询，则不冒险删除，保留会话交给后续维护；原始异常继续记录，登记状态不确定时以异常链保留原因，并返回提示先检查媒体库的受控 503。

## 期限与后台恢复

- 普通媒体上传会话有效期为 240 秒；原有上传锁过期窗口为 300 秒。原生读取过程中检查会话期限，登记时再以数据库时间核验。这不是同步任务的总时限，同步任务仍可缓慢推进。
- 上传创建 600 秒后进入回收候选。主站已有每分钟 Cron 的十分钟轮转中分配一个上传维护时段（分钟序号余数为 3），不新增 Cron 触发器。每次最多顺序处理 5 条；负载大或 Cron 延迟时，清理会稍后执行。
- 只通过 service_meta 主键范围按到期时间取候选，不扫描媒体桶或全部网站数据。
- 已登记媒体保留并结束会话；未登记对象执行幂等删除，只释放同一上传所有者的旧锁，保留新上传的锁。
- 未登记上传保留 24 小时回收标记，每 6 小时再次核对，覆盖通常的迟到写入；期满清理成功后删除标记。存储/数据库失败保留状态并延后重试，损坏状态不会阻塞后续候选。
- 清理不绕过权限或裁剪校验自动发布未完成文件。浏览器上传中断后需重新上传；本轮没有实现浏览器字节断点续传。

主站 inline/separate 两种部署均执行上述独立维护时段；separate 的同步任务仍只由专用执行器推进。首页、后台查看页面和同步状态轮询不会扫描或恢复上传会话。

平台硬终止仍可能打断任意位置，不能保证 finally 执行。持久会话让后续 Cron 能继续核对与清理，但不能保证在 Cron 被关闭、存储长期不可用或任意长时间悬挂写入的条件下完全没有残留。损坏会话会保留并记录错误，需根据日志排查，而非盲目删除对象。

## 诊断

- MEDIA-UPLOAD-SESSION：上传 ID、请求 ID、service_meta checkpoint。
- MEDIA_SESSION / MEDIA_EXPIRED：原生会话不存在、不符合状态或超期，受控返回 409。
- MEDIA-RECOVERY：上传 ID、原上传请求 ID、当前维护请求 ID及保留/清理结果。
- MEDIA-RECOVERY-ERROR：清理或重排失败阶段和受限异常栈，不输出正文或密钥。

## 部署

更新完整 v0.16.040 源码，沿用 Cloudflare 网页构建项目和 python build.py deploy。无需新增变量或数据库操作。现有流程自动更新原生辅助 Worker，再发布主站；必须部署完整包，因为主站与辅助 Worker 均新增会话协议。

保留主站已有的每分钟 Cron。主站暂停同步不影响上传残留维护。部署后正常响应 x-teacher-release 应为 0.16.040；上传日志应包含 MEDIA-UPLOAD-SESSION 和相同请求 ID 的原生结果。

先验证普通上传、媒体预览及首页；发生中断时可根据 upload_id 和 request_id 检查后续 MEDIA-RECOVERY。正常上传成功即移除会话，不需等待维护任务。

Ubuntu/Windows 上传路径保持本地存储逻辑，不启动 R2 回收，也不要求配置新变量。
