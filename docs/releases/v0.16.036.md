# v0.16.036 · 稳定性专项第七步：持久化降档与恢复

基于本分支 v0.16.035-isolation-step6。保留网站业务、三种同步模式、普通访问与执行器隔离，以及唯一初始化 SQL `database/schema.sql`；没有操作生产数据库或删除现有任务。

## 行为

| 情况 | 处理 |
| --- | --- |
| Cloudflare 可信遥测明确 exceededCpu / exceededMemory | 分别记录 CPU / 内存压力，自动调整开启时将正文切片减半 |
| 对端明确返回 1102，但无可信资源分类 | 记录资源类型未确认，减半正文切片，不臆测 CPU 或内存 |
| RPC 中断、执行超时、租约过期后的不确定中断 | 保守降档，但明确标注原因未确认，不把它们当成已证实的 1102 |
| 普通网络错误、HTTP 5xx、1101 运行异常、JSON 或数据库异常 | 保留详细诊断和原有异常处理；不凭这些信息自动认定资源超限、误缩小切片 |
| CredentialRetryError / 401 / 403 | 不降档、不放宽权限；按现有快速重试预算，前三次之后逐步延长等待，最多 1800 秒 |
| 正文分片成功写入 | 累计成功计数；至少 8 次成功，且距上次压力或调整至少 300 秒，才升档一次 |
| 升档 | 增加当前切片约 25%，至少增加 4 KiB，不超过任务初始值；升档后计数清零，并重新等待冷却期 |
| 自动调整关闭 | 不改变切片；仍记录错误类别和压力时间 |

最小正文切片遵守任务配置，绝不小于 4 KiB；初始值仍允许最高 4 MiB。持久进度增长时继续清零连续无进度失败，允许任务缓慢完成。授权被撤销、冲突、人工暂停和取消继续优先，不会被自动恢复绕过。

候选和重步骤已在此前降为一次一项，没有可继续降低的批量或并发值，本轮不重复引入批量状态。原生 R2 媒体仍使用既有流式多段上传及回执；正文切片降档不改变 R2 5 MiB 分段规则，也不宣称能消除媒体路径中的所有资源错误。

## 持久状态及事务

每任务最多一个小型记录：`service_meta / sync:adaptive:<task_id>`。保存成功计数、最近压力、最近压力类别、最近调整时间和策略动作，不保存正文、候选列表或媒体缓存，不依赖 isolate 全局状态。

任务完成一个步骤时，任务状态、切片大小、策略状态、事件日志在同一数据库事务内提交，并使用 attempt ID、lease token 和 revision 防止过期执行器提交。重复 finish、重复恢复、提交后应答丢失不会重复降档。策略写入失败时事务回滚，租约到期后仍可从已提交的任务断点恢复。

正文成功证据只在 StagingStore.append 已返回成功后设置于当前调用的 task 字典；它不跨请求保留。随后成功计数持久提交。即使超时保护将 handler 放在 asyncio 子任务执行，也能传递本次已确认成功的证据；若硬终止发生于提交正文之后、finish 之前，保留正文断点并保守降档，不冒充完整成功来升档。

候选发现、清单、空闲 tick、媒体成功不会计入正文升档成功次数。后台手动修改任务参数后，原有成功计数在同一参数事务中清除，防止旧计数立即影响新设置。修改失败或旧 revision 请求不会清除策略。已有任务无需迁移；没有策略记录时按初始策略工作。

负载策略记录损坏时，只重建这一份非业务元数据，并在事件中记录 state_reset；任务、正文和媒体 checkpoint 不变。策略读取在 SQL 中限制到 2049 字符再校验，不把任意大值载入运行时。

任务按原有规则删除时，策略记录随之分批清理，不额外保留孤立记录。本轮不主动删除任何已有任务。

## 管理界面及日志

任务详情新增持久化负载策略信息：当前分类、当前动作、最近压力类别及时间、最近调整时间、成功正文分片计数和升档条件。沿用现有样式和时间格式，查看详情只读，不唤醒执行器。

执行事件新增 adaptation，包括 before_bytes、after_bytes、retry_delay、checkpoint_retained、classification、last_pressure_kind、success_streak 等。较长诊断被裁剪时仍优先保留该小型策略信息。原有 request ID、task ID、PoP、阶段、checkpoint 和异常链继续保留。

## 验证边界

覆盖 SQLite 与 D1 契约适配器的事务回滚、丢失应答、重复 finish、租约过期、执行器重建、已取得进度后的中断、损坏策略重建、授权退避、升档冷却、4 KiB 下限和 4 MiB 上限。真实 HTTP 正文测试覆盖超时子任务中的成功计数。另验证后台只读详情、手动设置的 revision 防护及原有普通访问隔离。

Python 全量回归 632 项及 47 项子测试通过；随后新增的 6 项事务/参数/真实正文恢复测试也通过（定向回归合计 63 项通过）。1 项不适用于 SQLite 的 D1 丢失应答测试跳过，其 D1 分支通过。原生模块 51 项、后台 DOM/模型 7 项通过；inline / separate 离线打包及启动检查通过。D1 测试为本地契约环境，不是线上配额验收；未进行线上发布、真实 1102 强制终止或 CN/MXP 与 US/EWR 对照实验。没有注入国家或 PoP 特例。

## 部署与后续

使用完整源码包及既有 Cloudflare 网页部署命令；不增加环境变量、不手工执行 SQL。原有部署流程继续更新主站、原生辅助 Worker，并在 separate 模式更新独立执行器。

下一步建议是部署验收：核对所有组件版本及 separate 绑定，先测试连通性和小范围同步，观察主站访问与执行器同时运行时的请求 ID、断点、降档日志；再进行媒体与整站任务。若仍发生 1101/1102，用 Cloudflare 平台 outcome 配合 task ID 定位实际 CPU、内存或异常原因。没有线上日志前，不将某个 PoP 的持续失败归结为平台冻结，也不承诺单靠调整策略就能杜绝错误。
