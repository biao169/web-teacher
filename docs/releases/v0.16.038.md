# v0.16.038 · 媒体上传与同步专项第一步：分阶段诊断

基于本分支 v0.16.037。此步建立诊断证据，不宣称已解决线上上传后的 1101。普通媒体上传仍沿用有上限的完整缓冲，下一步再改造 Worker 原生流式上传。没有改变同步模式、签名、候选、审批、checkpoint、前台界面或数据库结构；唯一初始化 SQL 不变。

## 诊断范围

新增 `backend/app/ports/operations.py`，用请求局部 ContextVar 关联操作，不保存文件正文、下载缓存、任务或跨请求队列。只记录请求关联字段、固定阶段名、时间、大小、异常类型和最多六个项目代码栈帧；不输出文件正文、文件名、存储键、密钥、SQL 参数或原始异常字符串。

Worker HTTP 入口把既有 request_id、Ray、PoP、国家、组件和执行模式传入操作上下文。普通页面增加 handler 与 response-wrap 边界；首次创建应用另记 application-build。正常可包装的 HTTP 响应增加 `x-teacher-release: 0.16.038`，原有 x-request-id 保留。平台在代码外终止执行时，可能没有错误事件或响应头；不能据此宣称代码捕获了 1102。

媒体上传阶段：

- media-upload：整个上传调用，包括前置权限/配置错误。
- media-reserve：数据库上传占用标记。
- media-read-body：读取请求；成功后 MEDIA-BODY 记录实际字节数和上限，不逐分片打印。
- media-validate：类型识别和目的特定校验。
- media-quota：空间额度查询和检查。
- media-storage-put：存储调用；Worker 下进一步区分 r2-buffer-conversion 与 r2-put。
- media-checksum：现有摘要计算。
- media-register：媒体记录与审计事务。
- media-cleanup-object、media-release-reservation：失败对象清理及占用释放。

各阶段开始/结束/异常记录耗时或标记。长时间运行后没有 END 的阶段只是疑似中断位置，应结合 Cloudflare outcome、exception 和 Ray ID 判断，不能直接认定 CPU 或内存超限。原有 Worker 诊断继续区分可信平台 outcome 与未知资源类型。

## 原始异常与清理错误

修复既有 finally 清理异常可能覆盖原始上传异常的问题。上传失败后，对象清理和占用释放都尝试执行，普通清理异常分别记日志；若已有上传异常，继续抛出原始异常。没有原始异常时，清理异常仍抛出，不静默吞掉。日志标记 committed，便于区分“未登记成功”与“已经登记但释放占用失败”。

无法保证平台硬终止会执行 finally；本步不改变五分钟占用过期规则，也没有新增强制销毁 isolate、删除持久数据或批量清理逻辑。后续持久上传会话与恢复属于第二、三步。

## 同步连通性

`site_sync/runtime/bridge.py` 增加 sync-native-rpc 边界。RPC 调用成功不等于对端业务成功：后续 NativeError 仍通过既有诊断报告返回的 HTTP 状态、鉴权码与解码位置。

`site_sync/admin/connectivity.py` 返回 request_id、release、transport、executor_mode；原有 local_connection、peer_factory、signed_handshake、signed_candidates 保留，远端握手版本仍在步骤详情中。Ubuntu 路径为 ubuntu-http，Worker 为 worker-native-rpc。受控测试仍只读取候选，不创建任务或媒体。

源码中没有足够信息证明当前线上 1101 的具体原因，不能把“Ubuntu 通、Worker 不通”直接判定为某个密钥或内存故障。新增字段用于比对两端路径和实际运行版本。

## 部署后如何收集证据

1. 更新完整源码包，沿用部署变量和命令；辅助 Worker 仍自动更新。
2. 检查 Worker 正常响应的 x-teacher-release；连通性结果 release 应为 0.16.038。Ubuntu 也可通过连通性 JSON 和本地操作日志确认运行模块版本。这里只识别已执行组件，不宣称核验全部线上文件哈希。
3. 打开主站、执行器、原生辅助 Worker 的运行日志。先测试连通性，保留完整诊断 JSON。
4. 上传一个可重复触发失败的小文件，保留该 request_id 的 OPERATION 日志及 Cloudflare exception/outcome/Ray。
5. 随后访问一次首页，记录新的 request_id。比较是否卡在 application-build、http-handler 或 response-wrap；不要仅凭上传与首页失败的时间先后认定同一原因。
6. 日志中若只有 START，没有 END/ERROR，同时平台 outcome 为 exceededCpu 或 exceededMemory，则按平台证据分类；如果只有 1101，继续看异常栈，不猜测冻结状态。
