# v0.16.082 — 第五步：双平台故障回归与部署验收准备

本轮基于 v0.16.081，增加回归测试、修正旧测试的静态脚本版本断言并更新发布标识。没有改变同步协议、checkpoint、Executor、Native、业务表或 Linux 缓存/部署策略。没有执行线上部署；下列离线通过不等于 Cloudflare 真实资源额度验收。

## 验证范围

| 场景 | 结果及边界 |
| --- | --- |
| Local SQLite 与 Worker resource 分支：冷失败→恢复成功→正常访问 | GET/HEAD 均验证：503 no-store、恢复200 no-store、正常TTL及304；Worker分支是离线适配，不是真实D1 |
| simple / off | 不进入内部Page Cache；off正常页面no-store；simple正常30分钟缓存 |
| full旧成功页面 | 同表示过期后渲染失败返回旧200；Age递增、无缓存回写；过期窗口后503；刷新成功替换旧条目 |
| 恢复请求 | 不复用旧页、不生成正式缓存表示；成功有URL清理标记，不输出ETag |
| 前端恢复 | 只自动请求一次；二次失败停止；手动重试、pagehide清理、BFCache恢复及参数清理通过DOM测试 |
| 小助手 | 鼠标/触摸事件、视口限位、按钮避让、取消及监听清理通过DOM测试；本轮未重复真实浏览器视觉验收 |
| 隔离 | Admin优先转发、Sync路由边界、表单/fragment排除、正常取消与真实异常区分通过回归 |
| 平台强制终止 | 离线无法证明能捕获CPU/内存终止；不承诺恢复页能拦截所有1101/1102 |
| simple平台stale | 需线上验证实际PoP缓存命中/过期/淘汰；不能用内部Cache mock替代平台结论 |

- 286项Python测试通过；覆盖缓存/ETag、身份组件、预取/stream、故障恢复、Worker边界及角色隔离。
- 103项前端DOM测试通过；覆盖恢复页、stream、身份组件、导航保护、预取和浏览器缓存。

- 新增 `tests/test_public_acceptance_v082.py`：6组 local/simple/off × GET/HEAD 连续故障恢复测试，使用临时测试数据库，不修改用户数据。

## 部署验收顺序

1. 测试站部署此包；Worker保持 `TEACHER_WORKER_CACHE_MODE=simple`、`TEACHER_SYNC_EXECUTOR_MODE=separate`。不更改正式站数据库或任务。
2. Worker与Ubuntu分别运行已有只读探针（无需登录，不写数据）：

   ```bash
   python tests/probe_public_performance.py --origin https://YOUR-WORKER-DOMAIN --origin https://YOUR-UBUNTU-DOMAIN --expected-release 0.16.082 --output public-acceptance.json
   ```

   探针只测普通匿名HTML、重复请求与条件请求，不测浏览器缓存、边缘stale故障、CPU或内存。未返回发布头的平台不据此判定部署失败；核对部署包版本。禁止将 `release_match=false` 单独当作功能故障。
3. 浏览器打开 `/en/projects` 与 `/zh/projects`：确认成功200、30分钟TTL及stale指令；查看ETag/304。使用正常窗口和无痕窗口分别记录；不要清空全站缓存。
4. 打开 `/en/projects?__recover=1`：确认200且两个缓存控制头均no-store；页面加载后地址栏移除恢复参数；内容、语言及其他查询参数正常。
5. 在隔离测试站注入可捕获渲染失败（使用测试fixture或测试专用环境，生产不加故障开关）：冷缓存503恢复页→约1秒一次恢复请求→再次失败不自动循环；恢复后手动按钮可成功。HEAD无正文。Admin/Auth/Sync不出现该恢复页。
6. full在隔离测试环境验证同一版本旧页：已有成功条目、自然过期且未淘汰、渲染失败时200 STALE，Age不归零；新版本和 `__recover=1` 不回退。simple另行从实际平台日志确认缓存行为，不能把full结果当作simple证据。off确认不回退。
7. DevTools检查pagehide/BFCache返回、鼠标/触摸小助手限位和按钮可点击；浏览器未采用BFCache时记录实际结果，不伪造命中。
8. Cloudflare Observability按request_id/Ray/route核对原始异常仍有日志；记录colo、缓存状态、CPU时间、outcome、1101/1102数量和延迟。同步运行时普通Public/Admin仍独立。

## 验收记录建议

每条记录：部署版本、平台、缓存模式、URL/语言、是否恢复请求、时间、request_id、Ray/colo、HTTP状态、Cache-Control、Age、ETag、CF-Cache-Status（如有）、Worker outcome/CPU（如有）、结论。不得保存Cookie、授权头、同步密钥或私有正文。

真实Cloudflare缓存命中和错误恢复、Ubuntu/Debian实际服务部署、浏览器实际BFCache、CPU/内存指标目前均为待验收。不要将DOM模拟与本地SQLite测试写成线上测量。

下一步（第六步）：完成部署后的真实指标验收，核对不同PoP的缓存/恢复行为和错误率；根据实测结果决定是否需要额外修复，随后整理最终部署与验收记录。不得为了通过测试扩大Worker限额或改动同步执行策略。
