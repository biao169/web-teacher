# v0.16.048 — 克隆验证、D1 诊断与同断点隔离重试

基于 v0.16.047，仅针对同步验证与监控。未访问生产数据库、未部署线上，未取得任务325eafbd207744eba2433105f348ceb8的原始JsException。保留三种模式、500项候选规则、签名/媒体协议、所选内容、自动确认规则、task ID和已有clone checkpoint格式。没有数据库DDL变更，唯一初始化SQL仍为database/schema.sql。

## 排查结论

1. verify_tables使用selected_tables(scope)的固定顺序。包含restore_media_assets（包括教师资料的自动依赖）时，table=0是media_assets；不是所有选择的table=0都无条件是媒体。用户所述已传媒体且此前候选为restore_profiles的任务符合该顺序，但本轮没有直接读取生产scope_json。
2. 原源码clone.py第139行使用LIKE统计暂存数量。源码核对和测试确认其查询计划低效；现有错误摘要无法证明该行就是生产JsException的抛出点。读取inventory、JSON解析、COUNT、比较或保存checkpoint仍需用新日志区分。
3. 另一个已确认的问题：Worker的asyncio.wait_for在子Task执行步骤，ContextVar的细阶段更新没有自动回到外层异常处理。现在在请求局部task对象中传回执行结束上下文，并立即移除临时字段；不依赖isolate全局状态、不保存业务正文。

## 查询计划与范围

本地workerd真实D1 binding（Miniflare）放入100000条无关service_meta和3条目标记录，输出：

旧查询：SCAN service_meta USING COVERING INDEX sqlite_autoindex_service_meta_1

新查询：SEARCH service_meta USING COVERING INDEX sqlite_autoindex_service_meta_1 (key>? AND key<?)

D1返回rows_read=4，匹配3条。旧查询虽扫描覆盖索引而不是正文表页，仍遍历无关key；新查询仅查目标范围。这个测试不是Cloudflare线上额度或PoP验收。

使用WHERE key>=? AND key<?。克隆命名空间以ASCII冒号结尾：下界保留原prefix，上界只将末尾冒号改为分号。无LIKE转义/大小写依赖，key格式和协议不变；也避免media_assets中的下划线被LIKE当作通配符。计数、恢复取下一条、媒体引用映射、账号暂存和历史清理的相关key前缀查询均改成范围条件。

## 细阶段及错误

新增五个子阶段：

- clone-verify-table-load-inventory
- clone-verify-table-parse-inventory
- clone-verify-table-count
- clone-verify-table-compare
- clone-verify-table-save-checkpoint

console记录开始/结束/失败，含task_id、request_id、table、table_index、expected_count、actual_count、checkpoint_before/after、耗时及D1操作类型；事件日志保留最后细阶段和实际数据库checkpoint。每个子阶段不额外写D1日志；沿用每次tick的有界sync_events。清单读取上限16KiB，只加载所选表的元数据，不读媒体或正文。

D1适配器在prepare/bind/query/batch异常时附加operation、SQL类别、JS name、安全处理后的真实message、最多4个文件/行/列栈位置及耗时，然后重新抛出原异常。不记录SQL参数、完整SQL、正文、媒体、口令或完整原生stack；应用层错误链和Python文件/函数/行号仍保留。前端任务详情和展开日志可见D1原因。

## 同断点熔断

在既有sync:adaptive:<task_id>中增加可缺省字段，无需改表。指纹包含phase、sub_stage、table、checkpoint、progress_seq、异常类别/代码；不包含请求ID、调度时间等每次变化的值。

连续6次相同指纹且无持久进展，日志outcome为quarantined_retry；数据库状态仍为兼容的waiting，列表显示“同断点异常 · 低频重试”，下次至少30分钟后尝试。不删除任务，不回滚/重置业务checkpoint，不判永久失败。每次有效进展或成功步骤清除计数；变更断点/异常类别重新计数。旧任务从部署后首次可辨识失败开始积累，不能用旧的34次笼统计数推断同一细阶段。

管理员修复原因后可先暂停、待执行租约释放，再继续。继续会清除负载策略中的隔离计数，立即允许调度；保留实际下载/恢复断点。已有授权复核规则不变。

apply阶段不再因资源异常缩小正文/媒体切片。verify_tables执行的是SQL与清单检查，缩小slice无法改变COUNT查询成本；传输阶段保持现有切片策略。

## 监控与503

- 任务详情从轻量selection模块取表目录，不再为显示表名导入clone执行模块。
- 列表最多50项，以一次按页连接读取隔离标记，没有每行单独查service_meta。
- 详情只查当前任务；日志仍每页30条、每任务保留256条；不读取其他任务的完整日志或克隆清单。
- /api/status新增为只读任务列表别名，复用/api/tasks；不触发tick、apply或候选扫描。
- 旧全局控制API的活动租约查询最多51条，超过50明确标记截断；利用已有状态索引过滤，不再全表COUNT。
- separate模式的主站不推进同步，仍由独立executor执行。原有隔离回归继续覆盖。

模拟executor的COUNT连续抛JsException时，状态API返回200，详情可以读取；不能承诺共享D1本身不可用时监控仍200。生产503是否同一轮D1压力所致，现有信息不足以确认。任务列表现有created_at排序仍可能随历史任务数量增加而增加数据库排序成本，本轮未增加需要历史schema迁移的新索引；保留90天清理及分页，不宣称所有查询成本完全恒定。
