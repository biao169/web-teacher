# 历史记录保留 v0.15.105

## 策略与范围

- operation_logs：created_at 与 updated_at 均早于 180 天；单批最多 200 条。
- settings_audit：超过 180 天且 revision 早于当前 tool_settings 版本；单批最多 200 条。保留当前版本。
- transfer_allowances：创建、授权、到期及结束时间满足至少 90 天保留期；未结束但早已过期的预留也可清理。只识别现有离线任务 ID 和 relay: 在线任务 ID；授权时间缺失或未知任务类型保守保留。未完成的关联任务使明细继续保留。
- temporary_shares/recovery_tasks：必须同时标记 deleted，分享 manifest 已清空、检查点字节为 0 且 parts 为空数组、无清理错误或有效清理租约；创建/到期/最后更新时间均超过 90 天，无剩余分块/计量记录以及近期接收窗口或接收码；实际任务目录必须不存在。否则保留，不自动删除残留文件。

使用同一 HistoryPolicy 定义 180/90 天默认值，为第四步后台策略入口提供复用接口。目前没有新增可编辑的后台字段或数据库表。

## 配额保护

复用 transfer.backend.accounting.periods，计算 UTC 和 Asia/Shanghai 当前日、周、月所有起点，取最早起点作为额外保护边界。流量明细的授权时间必须同时早于保留期限和保护边界，才能删除。因此时区切换以及周/月跨界不会降低当前已用量或释放有效预留。常规 90 天保留已经长于这些周期，额外保护也适用于未来较短的策略。

## 关联清理与重试

每批按 ID 游标检查最多 10 个符合条件的任务。每个任务的成员、接收窗口、离线接收码、folder:ID: 元数据各删除最多 20 条，最后才删除主任务。复用现有事务断言，在同一事务内重新核对资格；任何步骤失败则回滚该任务的整个事务。父任务在关联条目清空前保留，不触发无界级联删除；已有异常/孤立数据不强行修复。

计量明细先按独立有界批次处理；本批开始时仍有明细的任务留到后续批次，预览不会把尚未符合条件的任务计入本批删除量。扫描游标固定覆盖 data/maintenance/history-cursor.json；有积压时继续，失败时复用维护任务重试。意外任务目录计入 retained_tasks，可由后续资源管理页面提示人工检查。

## 操作与边界

继续使用第二步的 cleanup-preview / cleanup-run / cleanup-status。预览不推进游标，不删除记录；结果包含 retention、counts、retained_tasks 和错误分类。状态是最近批次，不是累计。Windows 使用 deploy/windows/cleanup.cmd，Linux 使用 tweb，直接 Python 使用 python -m backend.cli 对应命令。

不更改数据库 SQL、表或索引；不清理业务内容、原媒体、译文、VPN 审计，也不执行 VACUUM。SQLite 删除后的内部空间供后续写入复用，文件不一定立即缩小。当前版本更新重启后会自动执行默认保留策略，超期历史将不可再查询。

## 验证

覆盖：180 天边界与分批/只读预览；UTC/中国时区当前全站与匿名用户配额前后一致；跨月/跨周和短保留策略保护；任务关联分批、父记录最后删除与外键检查；活动任务、近期记录、残留磁盘和失败清理保护；模拟事务中途失败回滚后重试；当前设置版本保留。实机 Windows 与长期负载验收留到第五步。

结果：75 项相关回归通过；最终资格条件微调后 8 项历史清理专项复验通过；命令行预览/执行/状态查询通过。数据库、前台及快传实现与 v0.15.104 逐文件一致。
