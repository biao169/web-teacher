# v0.15.130：第四步——执行、审批与后台调度复用分片复核

## 本次行为

- 拉取确认、接收方批准及发送推送提案，复用第三步的版本分页方法；每次请求推进一个表的一页元数据，检查点保存在原同步任务中。未完成确认复核时，不记录批准，不启动实际执行，也不发送提案。
- 浏览器沿用现有进度区、暂停按钮和顶部错误提示。确认复核暂停后再次点击确认；推送复核暂停后再次点击发送。打开最近预览也能继续。更改选择后重新建立对应复核检查点。
- 后台定时拉取使用同一套确认/执行方法，每次调度推进一个步骤；状态明确区分复核和已执行。不会自动批准远端提案。
- 媒体分片请求只查询对应媒体登记，校验登记摘要与存储对象版本、区间大小及哈希，不再每个区间扫描全部业务记录。旧媒体删除前只确认来源端对应登记仍不存在；接收端继续校验引用、登记版本和真实文件状态。
- 下载完成后进行分片提交复核；最终提交仍保留一次完整的来源版本检查。接收端复用恢复计划已读取的库存计算版本，并保留事务内库存条件和引用锁，防止覆盖并发修改。
- 批准记录、执行状态和审计在同一事务保存；复用任务状态比较保护，防止旧请求覆盖新进度。提交响应丢失时重新读取已保存阶段，避免重复提交。
- 执行错误复用现有诊断机制，返回阶段、分类和诊断编号，保留进度；不在错误提示中泄露 SQL 参数、连接密钥或业务内容。

## 保留的约束和边界

顺序仍为：准备新媒体 → 提交教师/学生/新闻等引用变更 → 处理旧媒体回收和删除。没有解除媒体引用约束，没有提供远程直接批准或任意业务写入接口。推送接收端仍需本地批准，连续推送仍按原最新提案机制处理。

协议为 **4**，请两站配套更新。更新前完成或取消旧的实际执行任务，更新后建议重新生成预览。数据库表结构、初始化 SQL 均与 v0.15.129 一致，**不需要重新初始化或重置数据库**。没有新增依赖。

限制保持不变：版本读取最多2000条/站、预览内容合计4MiB、实际选择最多500项；媒体单文件20MiB、单任务100文件/24MiB。分片降低单次请求的重复扫描和峰值负担，但会增加往返次数；后台按调度周期逐步推进，不承诺总耗时更短。

最终事务准备、差异计算和最后一次来源版本检查尚非完全增量处理；本版不能保证消除所有 Worker CPU 限制或 D1 500。出现错误时仍需用新日志的阶段及诊断编号判断。两站之间没有分布式事务，请继续遵循一人编辑、同步期间不再修改来源的工作方式。
