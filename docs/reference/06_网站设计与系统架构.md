# 06 网站设计与系统架构

## 设计依据

本设计仅依据当前源码、配置、迁移和测试重新梳理。`01_site_overview.md` 至 `04_admin_requirements.md` 是不可修改的目标与关键字段基线；当实现与目标存在差异时，应先记录差异，再通过新变更修正源码，不能反向改写基线掩盖差异。

## 系统定位

项目是一个面向高校科研团队的中英双语 Academic CMS。公开站负责团队、学生、研究方向、论文、项目、专利、新闻、课程和联系入口；后台负责对应内容维护，并提供媒体、翻译、账号权限、日志、导入导出等专项工作区。

## 总体架构

`app/` 使用 Nuxt 4 与 Vue 3。公开站启用 SSR；后台路径使用客户端渲染并通过统一 Admin Shell 提供侧栏、面包屑、权限反馈和工作区。`server/` 使用 Nitro/H3 文件路由，接口入口保持薄层，核心规则集中在 service，SQL 集中在 store、repository 或数据库适配器。`shared/` 提供前后端共同使用的契约和后台注册表。`db/` 同时支持 Node SQLite 与 Cloudflare D1。

## 运行时与部署

- Node/Ubuntu：数据库使用 `better-sqlite3`，媒体使用本地文件系统，缓存使用 Node 适配器。
- Cloudflare：数据库使用 D1，媒体使用 R2，缓存使用 Cloudflare 适配器。
- `nuxt.config.ts` 通过构建目标别名选择数据库、媒体和缓存平台实现，业务代码不直接依赖具体平台。
- 根路径重定向到 `/zh`；公开站提供 `/zh`、`/en` 两套路由；后台统一位于 `/admin`。

## 前端设计

### 公开站

公开页面按语言和资源类型拆分，页面层负责数据获取与 SEO，`app/components/public` 负责视图，`usePublic*` composable 负责请求和状态。富文本通过安全展示组件输出，媒体统一经过媒体路由或静态资源路径。

### 管理后台

后台模块以 `shared/admin/registry.ts` 和 `shared/admin/content-modules.ts` 为权威导航及 CRUD 定义。通用资源进入 `AdminContentWorkspace`；媒体、翻译、账号权限、日志、导入导出等复杂功能进入 `AdminComplete*Workspace`。统一列表、编辑器、操作列和快速跳转由 `app/components/admin/shared` 提供。

后台对象编辑统一使用 `app/components/admin/shared/AdminEditorShell.vue`。所有使用方均显式导入该组件，避免 Nuxt 按目录生成的 `AdminSharedAdminEditorShell` 自动名称与模板短名不一致。编辑壳提供顶部区块导航、返回、保存、保存并返回、脏状态提示和按对象生命周期注入的危险动作。页内编辑工作区把当前 UID 写入查询参数，使刷新、复制链接和浏览器前进后退可以恢复对象；完整对应关系见 `09_后台对象编辑统一设计.md`。

## 服务端设计

请求依次经过请求上下文、安全中间件、路由参数解析、权限检查和业务服务。认证采用服务端 Session、HttpOnly Cookie、CSRF 校验和可信来源限制；后台权限按模块与动作判断。数据库写入通过事务或原子批处理执行，重要操作写入 `operation_logs`。

## 数据与缓存

迁移目前定义 26 张表：`admin_mutation_guards`、`auth_bootstrap_state`、`auth_login_throttles`、`auth_permissions`、`auth_roles`、`auth_sessions`、`auth_users`、`cache_generations`、`courses`、`demo_seed_state`、`global_settings`、`media_assets`、`messages`、`navigation_items`、`news`、`operation_logs`、`patents`、`profiles`、`projects`、`public_action_throttles`、`publications`、`research_interests`、`site_settings`、`student_category_displays`、`students`、`translation_cache`。公开内容、翻译缓存、媒体元数据、账号会话和操作日志分别由领域 store 管理。缓存使用 tag/generation 方式失效，使 Node 与 Cloudflare 环境共享同一业务语义。

## 路由边界

- 页面入口共 67 个，详见 `07_项目目录规划与文件功能索引.md` 的 `app/pages` 部分。
- HTTP 接口入口共 88 个，详见索引的 `server/api` 与 `server/routes` 部分。
- 文件路由参数在文档中统一写为 `:uid`、`:slug` 或 `:key*`。

## 质量与发布

`tests/` 覆盖数据库、安全、缓存、公开站、后台、完整工作区与生产浏览器流程。`scripts/release` 负责源码一致性、可重复构建、运行环境、HTTP 回归和交付检查。修改共享契约或双平台适配时，应至少运行对应类型检查、单元测试和目标构建。

## 维护原则

1. 页面只装配，组件只展示与交互，composable 管前端状态，service 管业务规则，store/repository 管持久化。
2. 新后台功能先更新共享注册表与权限映射，再添加路由和工作区，避免出现“菜单有入口、功能没闭环”。
3. 新数据库变更通过递增迁移完成，不修改已发布迁移。
4. 新源码文件必须同步增加或重新生成对应源码说明；删除文件时同步清理索引。
5. `01–04` 永远作为需求基线保留原文。

## 第 4/7 步：默认语言入口

Ubuntu 使用 Nitro `node-server`；Cloudflare 使用 `cloudflare_module`（Workers Module）。根路径现在由 server/routes/index.ts 动态判定语言，优先级为手动偏好、IP 地区、浏览器语言、默认英文；显式 /zh 和 /en 不再被 IP 改写。共享规则、缓存、代理配置和验收见 `18_IP默认语言与手动偏好验收.md`。

## 第 5/7 步：站点地图与双语 SEO

公开索引入口为 `/sitemap.xml` 和 `/robots.txt`。地图复用 PublicContentStore 的公开可见性条件，按主键每 1,000 个 ID 分片，只查询地址字段；每个对象输出中英文 URL。共用 public-seo.ts 维护域名、canonical、语言关联和列表索引策略。配置方法、路由范围、抓取规则及验收见 [第 5/7 步说明](19_站点地图与双语SEO验收.md)。

## 第 6/7 步：共享编辑生命周期

七个主详情实现继续共用 AdminEditorShell；六个可写实现及只读日志接入 useAdminEditorLifecycle。路由改变前统一检查未保存修改，写入及确认期间共用互斥锁，异步详情只接受最新响应。媒体/译文不再自动推进冲突版本号，权限矩阵不因普通列表刷新丢失修改。详见 [第 6/7 步说明](20_后台编辑生命周期统一与验收.md)。

## 第 7/7 步：整体回归与交付

媒体列表、选择器、预览与编辑器复用 `useLatestRequest`，旧请求和卸载后的响应不再回写当前界面。`app/admin/media.ts` 统一媒体行、预览和统计的前端响应类型，`useAdminMediaUpload` 复用 `useCompleteAdminApi.csrfTokenForWrite`。未增加数据库结构和运行依赖。最终证据、源码说明覆盖和未完成项见 [21_全站回归与最终交付验收.md](21_全站回归与最终交付验收.md)。

## 前台第三轮正文与页脚优化

新闻列表不再拉取正文。详情正文按白名单转为Vue节点，图片和PDF均引用管理媒体；PDF接近视口才加载本地解析器，逐页渲染画布与文字层，页面自然增高。稳定PDF地址每次Range请求重新校验新闻公开性和引用，隐藏或移除附件后撤销读取。

全站布局挂载独立返回顶部图标。页脚正文仅由网站设置footer_text提供，可填受支持的HTML；首页与外壳通过同一函数生成footerHtml，不再自动拼接网站名称、版权、演示文案或系统署名。导航仍来自后台页脚导航配置。

翻译工作台可连续扫描并逐批执行当前可翻译队列。扫描游标覆盖表、记录和字段，随后分页校准旧缓存；队列在截断前过滤退避和耗尽重试项，返回下一次执行时间。浏览器页面负责调度，离开页面后不继续执行后续批次；不创建常驻服务或定时任务。见 [42_前台第三轮正文与页脚优化](42_前台第三轮正文与页脚优化.md)。

## 前台第四轮留言与请求稳定性修复

新闻详情按照allow_comments显示留言按钮，点击后加载共用ContactForm；未展开时不读取会话。普通留言页显式引用同一组件。表单故障在原位置重试，重复提交受pending保护，429遵守响应头冷却且不自动重放POST。新闻留言仍为后台收件，服务端确认新闻UID后在正文与审计保存来源，并在消息/审计原子写入时再次校验公开状态、发布时间和留言开关；无需新建数据库字段或迁移。
