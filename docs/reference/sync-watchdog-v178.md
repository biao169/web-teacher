# v0.15.178：三小时恢复巡检（第四步）

## 调度配置

部署配置保留每分钟 `* * * * *`，新增每三小时 `0 */3 * * *`。部署校验要求两条均存在，缺失三小时事件会阻止发布配置通过验证。本项目标准 `build.py deploy` 流程会生成包含两条事件的配置；仅替换运行代码而不更新触发器不会自动新增事件。

Cloudflare Cron 使用 UTC。新事件在 UTC 00:00、03:00、06:00、09:00、12:00、15:00、18:00、21:00 调度；对应北京时间每天02:00、05:00、08:00、11:00、14:00、17:00、20:00、23:00，不是从部署完成起计时三小时。平台实际到达可有延迟，配置传播也需要时间。

## 独立分支与恢复行为

最小 scheduled 入口在连接 D1 后通过 controller.cron 区分三小时事件。先写独立巡检心跳，再进入 watchdog 分支；不导入或执行分钟维护的快传清理路径，因此不会因整点 minute % 10 分配到快传清理而错过同步巡检，也不依赖 MEDIA 绑定来启动预检查。

巡检复用现有 SQL 调度器及 staged 模式，每次最多一次回执核对、预检查或业务步骤：

- 过期运行回执先核对真实持久化进展，再按原冷却规则等待。
- 尚未准备好业务的任务先保存预检查，后续分钟事件或后续巡检重新核对授权后推进。
- 分钟事件完全没有到达时，三小时事件仍能提供后续执行机会；如果需要多轮核对和预检查，可能跨越数次巡检，不保证三小时内完成恢复或任务。
- 不重置失败次数、不跳过冷却、不创建授权、不恢复用户主动暂停的任务、不批准推送、不批量删除租约或媒体。
- 有效任务锁和调度回执继续阻挡并发执行；过期租约由原正常获取租约的流程回收。分钟事件与巡检共用同一调度回执 CAS 和任务锁，不能重复推进同一步。

本步不新增全量任务扫描，不改变候选选择公平性及原调度准入规则。恢复有进展的任务仍可持续缓慢推进，无总任务时长限制。

## 独立诊断与页面位置

分钟 Cron 保持 `site-sync:cron-health`，三小时事件使用 `site-sync:watchdog-health`。两者各自保存到达时间、完成状态、版本、结果与错误类型/错误码，不互相覆盖。心跳增加随机轮次标识，防止同毫秒启动或迟到完成回执覆盖更新的一轮。

后台同步页“任务状态”列表上方新增“最近三小时恢复巡检”，显示预检查完成、中断回执已核对、冷却等待、本轮暂停或失败等结果。后台调度到达记录会标注“三小时巡检”来源。分钟 Cron 超过3分钟未到达仍单独提示，不能被刚到达的巡检掩盖；巡检超过3小时15分钟未到达也提示检查触发器。尚未跑过时显示“尚无三小时恢复巡检记录”，不会把新部署未到首轮当作已确认故障。

状态读取保持只读，仅读取两个小型心跳记录和现有任务投影，不触发业务执行。巡检心跳写入仍为尽力而为：D1 不可用或入口更早失败时不能保证数据库记录存在，需要平台日志。

## 验证与边界

50项 Python 检查分组通过，覆盖三小时入口在整点不进入快传分支、心跳隔离、故障记录、不加载业务的预检查、单靠巡检继续推进、过期回执和过期租约核对、权限/暂停/冷却/有效锁约束、与分钟事件并发、同毫秒迟到回执，以及部署包双 Cron 校验、既有轻量 HTTP 和最小 Cron 启动。5项前端测试通过，包含巡检成功不能掩盖分钟 Cron 停滞。

未部署到线上；没有把本地/模拟测试视为平台投递验收。两个 Cron 仍调用同一 Worker 的 scheduled 入口，无法修复共同入口初始化失败、缺失绑定、平台未投递或整个 Worker 不可用等情况。真正独立于该 Worker 的监测/唤醒需要额外的外部调度，本步未添加。

升级无需数据库迁移。部署后在触发器列表确认两条表达式，再在任务列表上方观察各自到达时间和巡检结果；如分钟事件正常但巡检一直没有到达，检查实际部署配置是否包含新增事件。
