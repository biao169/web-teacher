# v0.15.175：最小 Cron 启动路径（第一步）

## 修改目标

缩小 Cron 入口依赖，并把恢复预检查与业务推进拆到独立调度轮次。针对历史 Cron 低 CPU 即报错现象减少启动风险；没有真实平台异常详情，不能据此确认原始根因或保证消除 1101/1102。

## 入口与依赖

- Worker 顶层只预加载 SQL、轻量恢复/调度、绑定桥接和诊断，不再预加载网站、模板、字段/编辑器定义、快传或同步业务模块。
- 将共享 Error 移到 native/errors.py，catalog 保留同一类的导出，切断 D1 与诊断模块通过异常类导入完整字段定义的依赖。
- HTTP 所需旧预加载集合移入 http_snapshot.py，在网站应用构建时加载；ASGI、路由与快传也在对应事件内加载。
- scheduled 优先使用回调传入的 env，兼容 self.env；未显式设置数据库绑定名称时使用 DB。
- 入口立即输出 CRON-ENTRY；连接 D1 后先保存独立 Cron 心跳，再导入维护调度。此时尚未选定作业，心跳 job 为 dispatch，完成后更新为实际作业。数据库不可用时不能保证持久化心跳，仍需平台日志。

## 独立预检查轮次

每分钟 Cron 和既有维护时隙保持不变。同步调度的第一轮只做任务选择、授权及租约核对、恢复检查，保存 prepared / business_ready 回执；后续一轮再次核对条件后才加载并执行业务。必须有已完成、结果为 prepared 且授权版本匹配的回执才可进入业务。业务轮次消耗该预检查资格，下一次业务需要新的预检查。

中途暂停、角色/对端/授权变更不能沿用过期资格继续业务。强制中断仍依据持久化租约和退避恢复，不能依赖 finally 一定运行。旧任务无需数据库迁移。预检查、心跳及时间戳更新不算有效业务进展；没有添加总任务时长限制。页面显示“预检查完成，等待下一轮业务推进”。本地调度、手动继续及浏览器辅助唤醒保持原执行模式。

## 验证与限制

70 项 Python 回归测试通过，覆盖启动依赖、首次 HTTP 应用构建、Cron 心跳、轻量接口、历史恢复及初始化。随后加固预检查回执资格条件，8 项专项测试再次通过；6 项前端测试通过，含新状态文案与状态读取失败重试。启动验收检查禁止 Cron 预加载完整业务依赖及导入期间的运行时副作用。

以上是本地测试，未部署或测量真实 Cloudflare CPU。预检查拆轮会降低吞吐量；HTTP 定义从快照移出后，首次 HTTP 请求可能增加导入开销，需要部署后观察。业务轮次仍可能超限，本步骤不等于所有业务处理都已最小化。

未实现：大 JSON/长文本分片协议、媒体合并及校验的细粒度断点、自适应缩小当前内容切片、三小时独立巡检。下一步优先拆分大 JSON/长字段的读取、处理与持久化边界。

部署验收应确认：新版本号；Cron 到达时间随事件更新；预检查回执与后续业务回执交替出现；真实业务游标推进；暂停/权限变化后停止推进；首次网站访问与轻量状态接口正常。不要把预检查次数增长误当作业务进展。
