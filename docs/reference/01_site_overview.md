# 网站总功能描述

## 一、网站定位

本网站是面向高校教师、科研团队或实验室的个人/团队学术展示与内容管理系统。它既承担前台展示功能，也提供后台数据维护能力，目标是让教师团队能够持续维护学术主页、团队成员、论文成果、科研项目、专利软著、课程教学、新闻动态、联系留言、媒体资源和中英文内容。

网站不是单纯的静态主页，而是一个轻量级内容管理系统。核心数据以统一表结构保存，前台按访问语言和可见性过滤后展示，后台通过通用表管理与专门编辑界面维护内容。

## 二、基本内容范围

网站前台主要展示以下内容：

- 首页：网站名称、首页标题、副标题、代表性教师或团队入口、精选论文、动态摘要、导航入口。
- 团队/教师：教师、研究人员、学生等人员信息，含头像、简介、联系方式、研究经历、招生说明和学术链接。
- 研究方向：以标签或说明形式展示团队研究主题。
- 论文成果：论文题名、作者、期刊会议、年份、DOI、PDF、引用格式、作者高亮、收录信息和关键词。
- 科研项目：项目名称、来源、基金/计划、项目编号、承担角色、负责人、成员、周期、状态、经费和简介。
- 专利与软件著作：名称、国家、类型、申请号、授权号、日期、发明人、权利人、法律状态和证书材料。
- 学生：学生姓名、类别、年级、方向、状态、联系方式、获奖经历和毕业去向。
- 新闻动态：动态标题、分类、封面、正文、关联成果、发布时间、评论开关和展示状态。
- 课程教学：课程名称、学期、授课对象、简介、教学大纲、课件材料和参考资料。
- 联系留言：访客可提交合作、招生、论文、项目、课程等类型的留言。
- 媒体资源：图片、PDF、文档等可复用素材，供头像、封面、证书、论文 PDF、课程材料等字段引用。

后台主要提供上述数据的管理、编辑、筛选、批量更新、导入导出、权限控制、翻译缓存、媒体库和操作日志能力。

## 三、设计目的

网站设计目标包括：

- 让科研信息长期可维护，而不是一次性手写页面。
- 保证同一套内容可以同时服务中文和英文访问。
- 降低后台录入成本，通过辅助输入、媒体选择、富文本编辑和自动翻译缓存提升维护效率。
- 支持 Cloudflare Worker 与 Ubuntu/Debian 两种部署路径，使轻量服务器和边缘运行环境都可以运行同一套业务逻辑。
- 保持数据可迁移、可备份、可导入导出，避免平台锁定。
- 在低 CPU、低冷启动预算环境下仍保持前台和后台响应速度。

## 四、多平台部署要求

网站需要同时适配以下平台：

- Cloudflare Worker：使用 `src/worker.py` 作为 Worker 入口，前台静态资源通过 Workers Static Assets 提供，业务数据通过 D1 绑定读取和写入，媒体上传通过 R2 绑定写入。
- Ubuntu/Debian：使用 ASGI 应用入口 `app.adapters.ubuntu.main`，通过 uvicorn 运行，SQLite 数据库存放于 `data/site.sqlite3`，媒体文件存放于 `media`，由 Python 应用统一响应静态和媒体请求以保持行为一致。

两种平台需要保持数据结构兼容。`migrations/0001_initial.sql` 是 D1 与 SQLite 共用的基础结构来源；后续字段变更应通过迁移脚本同步到两类数据库。后台导入导出工具应作为跨平台数据互通的辅助机制。

需要注意：本网站中的文件传输工具属于单独功能域。当前传输工具依赖本地 SQLite 连接和本地运行目录，不属于 Cloudflare Worker 通用适配范围。主网站设计文档中的表结构说明不包含文件传输工具相关表。

## 五、数据互通要求

Cloudflare D1 和 Ubuntu SQLite 应使用一致的业务表、字段名、字段语义和可见性规则。字段新增时需要同时满足：

- `app/core/models.py` 中表模型已声明。
- `migrations/0001_initial.sql` 或增量迁移 SQL 已包含字段。
- SQLite 初始化和迁移工具可执行同一套 SQL。
- Cloudflare D1 可通过 Wrangler migration 或 D1 execute 应用迁移。
- 前后台渲染代码读取字段时应容忍空值，保证旧数据不会导致页面异常。
- 翻译缓存需要纳入新增的前台展示字段，避免英文模式下显示中文。

## 六、性能要求

Cloudflare Worker 场景下 CPU 时间有限，不能把页面渲染设计成频繁、多次、小粒度数据库请求。需要遵循：

- 进入请求时尽量一次性批量加载必要表数据，减少 D1 round trip。
- 前台列表页应使用分页、按需加载、虚拟列表等方式控制首屏数据量和 DOM 数量。
- 常用筛选项、媒体统计、翻译需求和高频公开数据可使用短 TTL 缓存。
- 后台概览页和列表页避免重复扫描全库，列表筛选使用统一查询和分页。
- 图片、CSS、JS、默认媒体等静态资源交给静态资产层缓存。
- 公开页面响应应尽量设置合理 Cache-Control，允许边缘缓存和短期 stale。
- 后台交互应优先采用异步接口和局部状态更新，减少不必要的整页重载并提供明确的加载、成功和错误反馈。

## 七、设计原则

- 表结构优先稳定，字段以通用文本/日期/布尔/数字类型表达业务，复杂功能通过约定和后台辅助完成。
- 前台只展示 `visibility=public` 或符合权限范围的内容。
- 后台必须先保证数据安全、可编辑、可恢复，再追求交互增强。
- 中英文内容优先读取人工字段，其次读取翻译缓存，再回退到原文。
- 媒体资源使用 object key 作为跨平台引用，不在业务表中保存平台绝对路径。
- 所有部署方式都应避免破坏已有数据库和已上传媒体。
