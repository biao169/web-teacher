本步骤承接0.15.66的同站共库整合，复用原Transfers、Accounting、Management与模板；只扩展快传需要的表、协议及前台交互，没有改变教师、论文等管理业务。

## 已完成

| 内容 | 实现 |
|---|---|
| 分块元数据 | 主站新增transfer_chunks，按任务与字节偏移建立索引；每次查询最多64块。point/manifest只保留固定大小的检查点，不再逐块重写全部parts数组。 |
| 上传确认 | 固定最大1MiB分块，文件刷新后才提交检查点。相同偏移、大小、SHA-256的已确认块可幂等返回；不同内容拒绝覆盖；并发冲突事务回滚，清除未被引用的多余块。 |
| 恢复上传 | 前台和快传管理页复用upload函数；逐页核对原文件摘要，确认版本不变后继续。未知创建结果不自动创建第二个任务。限速等待放在客户端，暂停可中止等待。 |
| 接收确认 | 新增transfer_receivers；每会话只允许一个尚未确认的块。写入接收流、提交ACK后才读取下一块。ACK响应丢失可重试同一个ACK，不重复写入/扣费。 |
| 流式保存 | 增加“检查文件→选择位置并保存”，支持本页暂停/继续/取消。每次只缓冲一个≤1MiB块并核验SHA-256，不拼接整文件Blob。最后close成功才显示“文件已保存”。 |
| 兼容下载 | 原“接收/下载”及分享URL保持可用，服务器改为分页读取分块。浏览器不支持逐块保存时明确使用原浏览器下载。 |
| 清理兼容 | 管理清理每次最多删除8块，按字节游标推进；失败可重试，不遗漏旧版部分清理任务。 |
| 资源准入 | 数据请求在读取正文前取得全站共享名额；满额立即503，不排队、不读取上传正文。直到流结束/取消才释放。主站普通页面不使用此名额。 |

## 当前使用方式

入口仍为 `/transfer/`，主站账号、端口、数据库均不变。

发送：选文件，点击开始；暂停后保留当前任务。继续发送会分页检查已上传文件内容。快传管理页复用同一个上传实现，未知创建结果请先核对任务，再到首页明确重新创建。

接收有两个入口：

1. **接收/下载**：保持原浏览器下载行为，不由网页缓存整文件。
2. **逐块保存**：仅在支持相关文件写入接口的安全上下文中显示。先检查名称与大小，再选择保存位置。保持本页面，可暂停/继续或取消。浏览器文件写入流在最终close前可能仍是临时文件；每块ACK表示写入流已接受，不等于最终文件已提交。关闭/刷新页面、浏览器崩溃后不承诺保留此临时文件；本版没有跨页面保存文件句柄。

浏览器支持边界及写入语义依据：
https://developer.mozilla.org/en-US/docs/Web/API/FileSystemFileHandle/createWritable

没有Windows真实浏览器测试证据，不把模拟DOM测试视为真实文件选取/写盘验收。

## 会话、权限与计量

- 检查分享只读取信息，不占用下载次数；选择位置后创建接收会话，沿用原配额规则预留此次临时文件下载量，并占用一次下载次数。
- 会话使用客户端随机密钥及确定性标识。相同密钥重试创建，返回原会话，不重复预留或累计次数。密钥不放URL；后续请求仍校验Origin、主站CSRF（已登录时）、当前身份和会话密钥。
- 一个会话最多有一个待确认块。最多重读当前块3次，ACK和重读不会重复扣同一块的逻辑额度；不能越过未确认块读取后续内容。
- `offered_bytes`记录服务端为响应准备的字节（包含重读），不是运营商带宽账单或接收方实际落盘字节。原Accounting仍计量唯一授权块；TLS/协议头、重传流量不计入这个逻辑额度。在线中转计量将在第五步单独明确。
- 正常完成或取消释放未用接收额度。会话闲置默认3分钟超时；若后台限速需要更久，租期至少覆盖两块的限速等待时间，且不超过分享有效期。即使浏览器突然关闭，过期预留在后续额度计算中只计已用量，不永久占用未用部分。
- 未确认创建结果时取消本地接收，不自动另建会话；可能存在的服务器预留按租期失效。取消请求失败时仍允许停止本地文件流，并明确提示服务器释放尚未确认。
- 暂停上传仍保留原临时分享文件与上传预留，截止原任务有效期；这里没有改变离线缓存保留策略。任务撤销/清理沿用原管理权限。自动清理属于第六步。
- 登出、禁用、角色变更、分享停止及版本变化会影响后续请求；已经送出的数据无法收回。

## 资源配置

本地启动环境变量：

| 变量 | 默认值 | 范围/含义 |
|---|---|---|
| TRANSFER_IO_CONCURRENCY | 4 | 1—8个并发数据请求（上传块、逐块读取、原分享下载合计） |
| TRANSFER_BUFFER_MIB | 16 | 4—64MiB应用缓冲预算；保守按每名额4MiB折算，实际名额取并发设置与预算折算的较小值 |
| TRANSFER_IO_IDLE_SECONDS | 30 | 1—120秒，无输入或ASGI发送阻塞时超时 |

上传块正文还具有120秒总接收期限，防止持续极慢输入长期占名额。单块最大1MiB；元数据页最大64条；接收确认窗口为一块。饱和返回503及Retry-After，不自动重放写请求。

上述预算是应用准入预算，**不是进程总RSS硬上限**。Python运行时、主站、TLS、SQLite、网络和浏览器缓存仍占内存。主站启动器继续沿用整体HTTP并发限制；没有新增监听端口。当前没有WebSocket文件通道，WSS框架队列与中转背压在第五步落实，不能把这一步当作完成在线中转。

## 从0.15.66升级

1. 停止主站，保留原配置、数据库和完整transfer-data目录。
2. 在新代码目录使用同一Python环境与配置执行 `upgrade-data.cmd`；Linux执行：

```sh
python -m backend.cli migrate
```

工具识别原结构并创建数据库旁的 `.before-v0.15.67.sqlite3` 快照，新增0015表和索引，在同一事务内转换旧parts。保留任务ID、分享令牌哈希、有效期、额度与文件路径；不移动或删除文件。不符合条件就回滚数据库修改，不通过重置升级。

旧单任务parts JSON超过8MiB时拒绝自动转换，要求停服离线核查，防止迁移一次装入异常大历史清单。旧版已清理和部分清理任务均有专门兼容；清理游标转换为字节位置。

3. 启动主站，检查原任务、一次上传/下载和分页恢复。切换源码目录仍须保留transfer-data，不能用新包覆盖删除它。

首次从独立旧快传迁移时，继续使用第二步的 `python -m transfer.backend.migrate import ...`，新版本已同时接入0015及旧parts转换；详细来源路径和收据命令见 `transfer-integration-v66.md`。

回退0.15.66需要停服并恢复本次升级前的数据库快照，同时使用原代码和对应文件。不要在产生新任务、清理文件或其他业务写入后直接恢复旧快照，否则会丢新数据或引用已删除文件。迁移快照不是允许忽略新数据的强制回滚工具。

## 当前边界与下一步

当前对用户开放的仍是原临时分享模式，继续保留200MiB上限和原后台限额。没有宣称已经支持不限大小的在线传输、真实局域网直连或跨网实时中转。Windows/手机文件选取与真实写盘、多设备网络、生产VPS并发内存与多GB实传仍待后续验收。旧独立Worker适配未升级为主站统一模式，继续保留原实现。

下一步为第四步：同站配对/信令与WebRTC DataChannel，复用分块、确认和保存组件，验证局域网文件字节不经过服务器，并正确提示隔离网络无法直连的情况。
