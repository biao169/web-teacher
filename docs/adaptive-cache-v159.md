# v0.15.159：第五步，响应与自适应缓存

基于本轮 v0.15.158，保留同步模块独立目录、数值字段显示、原始图标、多域名和日志管控。无需数据库结构修改，无需删除已有缓存目录。

## 实现方式

### Windows / Ubuntu / Debian

沿用并优化已有匿名公共SQL缓存：默认配置上限32 MiB，实际预算取配置上限、系统或容器总内存/256、可用内存/64中的最小值，并按 WEB_CONCURRENCY 分摊。可用内存低于64 MiB时预算归零；最多每15秒重新探测系统和cgroup限制。预算缩小时，在后续访问中立即淘汰超额条目。

本步把每次命中时遍历全部条目的过期清理改为最多每秒一次扫描；访问目标条目时仍精确检查过期时间，不延长TTL。关闭缓存时不再序列化待缓存结果。缓存包含LRU和原有条数/单结果上限，普通查询TTL仍为30秒，时间相关查询TTL仍为1秒。

沿用数据库与WAL文件指纹以及本进程写入失效机制，检测本进程、其他连接写入和数据库替换。公开可见性、导航、译文更新继续经过这些校验；权限、身份、操作日志、同步状态等读取绕过公共缓存。

调整本地环境变量：

```dotenv
TEACHER_PUBLIC_CACHE_MB=32
```

设为0关闭本地公共SQL缓存；配置允许0～64 MiB。它是缓存预算，不是整个Python进程的内存上限。

### Cloudflare Worker

采用独立的保守策略，不使用本地系统内存探测结果：

- 只在匿名公共GET请求中复用站点配置和全局配置读取。
- 每个请求缓存预算最多64 KiB，单结果最多16 KiB（包含记账开销），最多32项、每项最多64行。
- 普通列表、翻译、身份、权限、同步、时钟和随机查询不写入该缓存，避免为不重复的业务查询增加序列化成本。
- 统一页面与公共布局的站点配置查询，使其在同一次请求内复用；请求之间不共享SQL结果。
- 返回结果为独立副本；经包装器写入时清空缓存，写入失败和并发旧查询返回也不能重新填入旧结果。
- 打包模板使用24项编译模板LRU预算；缓存的是模板代码，不是带账号信息的页面HTML。

Worker绑定变量可设置 `TEACHER_WORKER_REQUEST_CACHE=0` 关闭请求内配置缓存；缺省开启，其他值也视为开启。该开关不改变模板24项上限，也不配置本地磁盘缓存。

64 KiB是单请求缓存预算，不是整个Worker或所有并发请求的内存上限。下一次请求重新读取数据库，所以后台保存、同步写入、导航和可见性修改无需等待跨请求TTL到期。正在执行的同一次请求可能继续使用已读取的配置。

## 账号和响应隔离

先解析会话，再决定是否缓存。已登录用户、后台、登录、快传与同步管理不接入新的请求缓存。动态HTML/API继续保持原有 `Cache-Control: no-store`，不把个性化整页交给浏览器/CDN共享缓存。中英文与不同查询参数按完整SQL和参数区分；不会绕过现有权限规则。

本步不更改媒体内容缓存、离线快传缓存或站点同步检查点。

## 测量与验证

包内可复现脚本：

```sh
python -B tests/benchmark_public_cache.py
python -B tests/benchmark_request_cache_v159.py
```

结果分别在 `local-cache-v159-benchmark.json` 和 `request-cache-v159-benchmark.json`。使用本地TestClient、SQLite和演示数据，每项5次；第二个脚本模拟Worker代码分支，不是线上D1/Worker性能测试。

本次配置缓存使首页、项目页、学生页SQL调用分别从31/33/37降至30/32/36。这个结果证明减少了一次配置查询，但本地耗时存在波动，不能声称每页都更快或推算真实Worker提速比例。

本地缓存开启与关闭的对照用于验证现有缓存仍有效，不代表这些全部收益由v159新增。新增过期扫描优化另有测试验证：连续100次命中不会每次扫描全部缓存条目。

回归包含真实页面、后台修改后的下一请求可见性、隐藏内容、翻译/导航失效、跨连接数据库写入、预算缩小、过期、写入失败、身份隔离，以及前四步和Worker启动/同步调度。准确结果见 `adaptive-cache-v159-tests.json`。尚未完成真实Cloudflare、Windows生产进程和VPS部署验收。
