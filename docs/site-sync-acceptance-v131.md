## 两站部署后验收（尚未执行）

1. 先在原版本完成或取消正在执行的同步任务，暂时关闭自动拉取。上传完整发行包到部署分支，不遗漏发布清单；部署两站。本版协议仍为4，与v130协议一致，建议两站统一至v131。
2. 保持原 D1/SQLite、R2 和站点连接配置。无需更新数据库表、初始化或清空数据。进入后台同步页，双向分别点击“测试连接”。它只验证连接/签名/字段协议，不代表业务数据已全部验证。
3. 一次只选一端编辑。创建专用验收条目及小图片，在另一端预览、选择、拉取，确认新增/修改字段和媒体预览正常。反向再操作一次。普通用户不得看到管理字段。
4. 验证依赖删除：让验收教师或新闻先引用媒体a，再在来源端改用媒体b后删除a；接收端选择删除a时应带上必要的引用更新。完成后b可预览、旧引用消失、a的登记和文件按选择删除。不要拿正式媒体做首次删除测试。
5. 验证推送批准：连续发起两份不同选择的提案。接收站核对最新提案，旧审批应失效；未批准时业务记录不改变。批准后只有当前选中的变更和必要依赖执行。
6. 复核或传输时点击暂停，打开最近预览/任务后继续。失败时先看已保存阶段和“数据库已提交/尚未提交”，不要反复新建任务掩盖原错误。若来源变化导致409，应重新预览；已执行任务先完成或取消。
7. 手动同步通过后，再仅在接收站开启定时拉取。一次调度只推进一个阶段/分片，请观察多次调度进度；“当前周期未完成”不等于失败。切换主站前关闭原接收站策略，避免两端同时自动覆盖。

可复用原公开页面检查脚本，在自己的终端运行：

```bash
python deploy/cloudflare/smoke.py --origin https://web-teacher.2948531734.workers.dev --repeat-startup
python deploy/cloudflare/smoke.py --origin https://vip.moglider.com --repeat-startup
```

该工具只检查公开HTTP入口，不能替代后台审批及同步验收；首次访问快传入口可能初始化其默认配置。遇到访问规则阻断，应先在自己的服务端确认规则，不要通过更换来源绕过。

## 线上失败时记录什么

| 现象 | 需要核对的证据 |
|---|---|
| 进入同步页1102，随后1101 | 对应请求的Worker异常堆栈、CPU/资源指标、时间及Ray ID；不能仅凭HTTP代码判定数据库问题 |
| 对端500或本站数据库错误 | 两端对应诊断编号、阶段、错误分类；分别确认错误发生于版本页、快照写入还是实际提交 |
| Ubuntu502 | Ubuntu服务日志及代理日志；若没有应用诊断记录，先核对请求是否进入应用 |
| 409版本或引用变化 | 原任务阶段、来源/目标最近编辑；重新预览并核对选择，不关闭检查强行覆盖 |
| R2失败或媒体不显示 | 配置桶名、绑定、媒体/缓存前缀、对应对象及阶段；不要仅以是否显示“文件夹”判断 |

分享日志时保留阶段、分类、诊断编号和时间，去除密钥、Cookie、密码及令牌。线上性能结论应基于该批数据和真实Worker运行指标；本地适配器测试不产生真实Worker CPU成绩。
