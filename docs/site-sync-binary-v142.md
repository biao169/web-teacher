# v0.15.142：第三步，媒体二进制分片

## 本次行为

两站均升级后，媒体头信息声明二进制分片能力。接收站每次只请求一片，原文件正文最多 64 KiB；小型 JSON 元数据签名后与原始二进制一起返回，不再将文件正文转换成 Base64 或纳入 JSON/HMAC 序列化。

64 KiB 原文原先转换为 87,384 字节的 Base64，现在仍是 65,536 字节；这是正文编码体积的减少，不是实测 Worker CPU 降幅。接收端只做一次分片摘要检查，随后沿用缓存写入和偏移量检查点。

复用同一个同步接口、HTTPS 传输、公共地址限制、证书校验、错误诊断和超时。响应仍校验签名、请求随机数、对端身份、媒体版本、偏移、长度和摘要。二进制帧的元数据最多 8 KiB，总响应最多 73,736 字节。业务数据接口仍使用现有 JSON。

## 恢复、发布与清理

- 分片写入成功之后才保存偏移量。写入确认丢失时，重试覆盖同一个确定性缓存键，不追加重复字节。
- 现有任务已保存旧版媒体头时继续走旧 JSON 分片；旧对端未声明二进制能力也沿用旧方式。已协商二进制后遇到错误不静默降级，保留检查点供重试。
- 继续复用原生流式合并：每个请求最多合并四个缓存对象；合并游标、整文件校验、发布及清理仍由原有阶段推进。没有新增整文件 Python 内存缓冲。
- 整文件摘要和同名文件一致性检查仍保留；没有把文件存在误当成内容一致。来源文件读取期间变化时中止。
- 取消/完成复用现有逐批清理。目标已有、已登记媒体保留；来源永久删除不要求目标删除。

## 部署

更新两站到 v0.15.142，不需要修改数据库表或重置数据。协议 7、任务格式 8 未变。部署脚本不恢复源码完整性强校验。正在执行的任务建议先暂停，更新完成后继续；首次测试可使用一个小文件，再测试多分片媒体及暂停恢复。

## 边界和下一步

本步减少编码与重复计算，不保证消除所有 1102/1101。整文件摘要和最终发布仍各占一个请求；R2 原生流的实际 CPU/内存需线上观察。文件大小上限（单文件 20 MiB、每任务合计 24 MiB）未改变。

旧任务、接收方审批复核、定时拉取仍有旧版完整准备流程。下一步将处理这些入口与逐条执行引擎的统一，检查公共初始化和重复查询，并完善阶段耗时信息，以实际触发超限的阶段为准继续降低开销。审批授权和必要认证不省略。
