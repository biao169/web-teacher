# v0.15.150：第四步，自适应媒体分片

## 本次行为

两端新版通过签名 media-head 响应协商文件分片大小：任一端为 Worker/R2 时使用16 KiB，本地服务器之间64 KiB。每个文件第一次读取头信息时保存 chunk_bytes 和能力标志；后续下载、重试、合并、发布及清理始终使用该值。

旧对端不声明能力时保持64 KiB。已开始下载的旧任务没有新字段，默认继续64 KiB；不修改旧偏移和旧合并路径。不能为了省内存把正在执行的旧任务强制缩小分片，否则合并会缺段。

每次仍只传一个分片。二进制读取缓冲上限随协商大小缩小（另加有限的签名头部开销）。协议原有64 KiB硬上限保留，兼容旧响应；收到内容仍核对实际偏移、长度、版本、签名。JSON/Base64旧格式继续兼容。

合并复用原生流及原四路合并算法，只改变初始分片宽度；合并中间对象名称区分原始分片与合并层。清理从对应初始宽度继续，Worker每次最多删除一个暂存对象，本地最多四个。保留源文件版本检查、最终摘要、类型核对、引用保护和防止覆盖同名不同内容文件的逻辑。

## 资源与速度

16 KiB相较64 KiB降低单次分片字节量，但会增加约四倍下载请求以及更多合并/清理步骤。按分钟推进的自动任务会更慢。最终流式合并、完整性摘要和发布仍处理整个文件，不能把整个请求或整个同步的CPU/内存解释为固定16 KiB，也不能保证消除所有1101/1102。R2使用原生流；本地原有流缓冲不变。

## 更新与兼容

在v149基础上覆盖补丁相对路径，两端重新部署后新的文件头协商生效。无需数据库初始化、迁移或重置；协议7、任务格式8不变。不会覆盖独立多实例部署脚本、前台自定义教师模板。已经协商16 KiB的任务若把对端降级到旧版本，应更新回新版再恢复，不能强行用旧端继续小分片。

第三步最新500项规则保持。下一步完善失败退避、恢复及重新开始操作，避免失败后连续高频请求。
