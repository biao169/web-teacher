# v0.15.143：第四步，统一低负载审批与定时同步

## 完成内容

新建手动拉取、接收方审批及定时拉取共用已有按需准备、逐条执行、二进制媒体和恢复逻辑。本次没有新增生产模块、依赖或数据库表。

审批不再建立全库快照：每次读取一个提案指定记录或引用，必要依赖仍在确认前准备好。准备完成后可多选、全选或清空；依赖由数据库按已准备的记录键补选，不读取完整业务正文。执行仅使用最终选中集合，未选中的已准备记录和媒体不会执行。已开始执行后选择锁定。

定时任务先分批收集所选模块的简要候选，每次最多20条；保存选择后进入同一个按需准备流程，每次实际执行最多提交一条业务记录。媒体仍每片最多64 KiB。审批不会被定时任务自动批准：后台只推进已确认任务，或按本站显式保存的定时拉取授权发起任务。

目标记录的基础字段和版本合并为一次查询，不读取目标长正文；发送提案移除重复连接探测。现有任务进度中新增 `elapsed_ms`，页面显示最近步骤耗时，不新增日志表或额外日志写入。该值是步骤耗时（含等待），不是 Worker CPU 时间。

## 操作与行为变化

1. 两站更新到 v0.15.143，先测试连接，再开始新任务。不需要修改表结构或重置数据库。
2. 手动拉取仍是“选候选 → 准备 → 核对并确认”。接收推送则“重新读取提案 → 准备完成后勾选 → 输入确认文字批准”。发送方多次提交，仍由最新待批准提案替换旧提案，旧批准不会继承给新提案。
3. 提案等待期间条目被修改，复核读取当前内容；准备后所选来源或目标记录又变化，在执行该记录时停止。已经提交的条目保留。必要时取消并清理旧任务，由发送方重新提交新提案，或另建手动拉取；不恢复为整任务原子回滚。
4. 双方都已不存在的指定条目可跳过。来源已永久删除的媒体也跳过，目标已有媒体记录和真实文件保留。必要依赖缺失仍会停止，不能把缺失依赖当作已准备成功。
5. 相同编号仍是覆盖候选，不比较全文。因此相同正文可能再次写入；定时任务也不再承诺“无内容变化则零写入”。每个任务最多500个条目及依赖，超限停止，不能将模块范围任意截断后继续删除。较大的模块请改用手动筛选分批。
6. 定时间隔控制下一轮任务启动；执行速度取决于本地后台循环或 Worker Cron 的调度频率，不能把5分钟间隔理解为保证5分钟内完成全部数据。
7. 失败后继续原任务、取消清理和重新开始沿用已有入口。审批需要重新复核或新提案，不能通过“重新开始”继承授权。

## 兼容与边界

协议7、任务格式8及业务SQL结构不变。旧版已经创建的详细快照任务保留既有断点流程；本次优化针对新任务。账号、权限、私密部署配置和快传临时文件不加入同步范围。部署脚本不恢复源码完整性强校验。

本次验证使用真实本地 SQLite、文件和模拟 D1/R2 绑定，不能替代 Cloudflare 线上 CPU/内存验收。R2 原生整文件校验与发布仍各占一个请求；单条来源正文上限200KB、单文件20MiB、每任务媒体24MiB未变。不能保证所有1102/1101均已消除。

## 下一步：两端实际验收

先以少量记录和一个媒体文件测试 Ubuntu → Worker，再反向测试；核对审批子集、待批准提案替换、暂停/继续和断网恢复。随后逐渐增加数量，记录发生1102/1101时的阶段、最近步骤耗时、Ray ID及 Cloudflare CPU 指标。若仍超限，应按实际阶段继续拆分，而不是仅缩短或拉长请求间隔。

## 验证结果

111项不重复测试通过：90项Python回归与21项后台DOM测试。覆盖最新提案替换、接收方改选、依赖补选、缺失媒体保留、逐条写入预算、调度授权撤销、失败恢复、模拟D1/R2三种组合、二进制媒体与Worker启动。修改后按逐条提交语义修正了一项旧恢复测试，并复测通过。无生产环境请求或写入；测试明细见同目录JSON文件。
