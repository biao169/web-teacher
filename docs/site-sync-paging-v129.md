# v0.15.129：第三步——分片版本检查与预览分页

## 本版变化

预览按四个阶段持久化推进：

1. baseline：两站逐表建立版本基准与记录总数。
2. content：按 UID 游标读取内容，写入原有 sync_task_items。
3. verify：两站再次逐表读取版本，核对摘要和记录总数。
4. done：生成依赖关系、差异和勾选结果。

开始预览只做轻量连接检查和创建任务，不同步读取全部业务版本。每次 advance 只处理一个版本分片或内容页，游标、阶段和增量摘要保存在原有 sync_tasks.state。暂停后从保存位置继续。

版本分片每次最多处理100条 UID/updated_at，SQL最多读101条以判定下一页。只传摘要、条数和游标；每个分片1次业务查询。逐表增量摘要与执行前原有完整版本检查使用同一算法。

内容每页仍最多20条、保留大小限制；只进行当前页大小预检与内容读取，业务查询从5次降为2次。删除每页两次全站扫描和一次 COUNT；完整数量由基准阶段累计并保存在任务中。以上不包括身份授权、任务进度和快照写入所需查询，不代表一个HTTP请求总共只有2次SQL。

阶段增多意味着请求次数可能增加，小型网站未必总耗时更短。目标是避免单个内容页重复扫描全站，将预览读取成本从随页数反复扫描降为有限轮次的版本读取加内容读取。

## 一致性与并发

- 分页累计条数必须匹配基准；空页、错误游标、缺失记录不能形成删除预览。
- 内容读取后必须复核两站完整版本；同样条数下的正常内容修改（updated_at变化）也会令任务停止。
- 复用 admin_mutation_guards，在同一事务中比较任务原状态并写入快照和新进度。并发推进的旧状态回滚，避免空页或浏览器/后台并发覆盖游标。
- 未到最终复核完成阶段不能生成差异。
- 提交、审批、媒体传输等原有执行前版本检查继续保留，不放松媒体引用更新后再删除的约束。

本步没有把实际提交、审批、媒体每个区间的版本检查全部改为分片，也没有重写最终差异比较。这部分按第四步继续统一优化。当前完整版本检查仍有界于2000条/站，预览总内容上限4MiB，未提高这些限制。

## 更新要求

协议升级至3、任务预览格式升级至3；两站配套更新 v0.15.129 或后续兼容版本。旧预览重新生成，不复用旧算法摘要。数据库表及初始化SQL没有变化，不需要迁移或重置，业务数据不受影响。

升级前先完成或取消旧版已经开始的实际同步任务，并暂停自动同步；旧任务格式不会在新版继续执行。新版中的旧任务会明确提示重新生成预览。若已升级但仍有旧的实际执行任务，应先用对应旧版本完成/取消后再更新，不要手动删业务记录解决。

测试连接仍是第二步的轻量操作。若出现D1异常，继续用第一步新增的阶段、分类和诊断编号定位。本版未连接生产网站，不宣称已确认线上错误根因或所有CPU超限均已解决。
