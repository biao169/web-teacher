## 发送和接收

1. 打开网站的文件快传页面，选择适合双方的模式。局域网和在线中转需要双方在线；临时分享上传完成后可稍后接收。
2. 选择文件或文件夹。在线配对创建完成、文件夹清单封存后显示传输码；临时分享上传完成后显示码及原分享链接。
3. 将六位码发给接收方。接收方在“使用六位码接收”输入代码，系统自动切换到对应功能区。
4. 核对文件名、大小，再点击保存按钮。支持目录写入的浏览器可按原层级保存文件夹；不会强制转成压缩包。不支持所需保存能力时会提示。
5. 网络结果不确定时保留原页面重试。码获取失败可单独点击更新，不需要重新上传。旧的 32 位在线配对码及原分享链接继续兼容。

六位码不保证永远有效：在线房间结束、离线租约到期、撤销或策略变更均可能使接收失败。撤销码阻止新的解析和接收授权；已经建立的传输需用原取消操作停止。有效期、额度和下载次数仍由后台控制。

## 后台

教师后台侧栏进入“文件快传”，直接在右侧操作。只有查看权限时只显示自己的任务；工具设置、全站任务和缓存管理继续要求查看、编辑、删除权限。开发测试示例区默认折叠。

设置保存继续检查 CSRF 和设置版本；保存失败保留草稿，任务局部刷新不会重载设置。缓存删除仍使用原有预检与分批处理。旧管理 URL `/transfer/admin` 验证权限后跳转至 `/admin/transfer`，保留筛选参数。

## 更新与部署

- v0.15.95、v0.15.96、v0.15.97 和 v0.15.98 的数据库 SQL 与校验快照一致，均为 42 张表。这些版本之间更新源码并重启即可，不应为升级而重置数据库。
- v0.15.94 及更早版本结构不同，缺少 `transfer_codes`。按用户的新站开发约定使用明确重建操作；不会自动迁移或自动清库。
- Windows：所有 `.cmd` 位于 `deploy/`。`deploy/windows/start-existing.cmd` 保留当前数据；`start.cmd` 明确重建开发数据库，两者用途不同。
- Ubuntu/Debian：根目录 `install.sh` 默认使用上述 GitHub 仓库与分支。把域名等真实配置按根目录 README 填写。后续使用 `sudo tweb update` 更新已保存的来源；普通更新不清库。
- GitHub：将 `teacher-site/` 内的全部源码置于分支根目录，包含 `.gitignore`、`.gitattributes` 和 `release-manifest.json`。不要提交数据库、媒体、密码配置或 `deploy/windows/local.cmd`。源码修改后重新生成发布清单。

本轮没有替用户上传 GitHub、安装公网服务器或改动生产数据库。

## 验证与限制

最终全站回归：**727 项 Python 测试、255 项模拟 DOM 测试全部通过，共 982 项**。结果摘要见 `transfer-release-v98-verification.json`。

自动化包含主站回归、管理权限/CSRF/草稿保留、三种模式的短码解析、文件夹流程、Git 本地克隆后的字节校验、部署脚本与单端口服务启动。

真实本机 HTTP 测试使用临时合成数据：两个客户端通过六位码配对，中转 8 MiB 数据并校验摘要；主站同时保持可访问，确认中转不落盘。另测临时分享通过派生令牌下载、配额计数、服务关闭重启后六位码仍可解析。它不等同于真实跨设备局域网 WebRTC 或公网 WAN 测试。

仍需在实际环境确认：Windows Chrome/Edge 的文件/目录选择和保存、两台设备的 LAN 直连路径、公网 HTTPS/反向代理下的长时间传输。此次没有执行真实 systemd 云部署或浏览器人工视觉验收。

复验入口（项目根目录，先安装测试依赖）：

```text
python -B tests/run_acceptance.py --dom --report data/acceptance/v98.json
```

Windows 可运行 `deploy\windows\test.cmd --dom --report data\acceptance\v98.json`。测试依赖及 Python 路径说明见 `tests/README.md` 与 `deploy/windows/local.example.cmd`。测试使用临时数据，不连接生产数据库。
